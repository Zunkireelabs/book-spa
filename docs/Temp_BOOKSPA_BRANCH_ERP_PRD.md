# BookSpa — Branch Operations ERP
## Phase 1: Excel Replacement First
### Project Context & Product Requirements Document (PRD)
### Version: v1.0 — Scope Locked

---

# 1. Executive Summary

BookSpa is being built as a **Branch Operations ERP system** for spa businesses.

The primary objective of Phase 1 is to **replace the client’s daily Excel Sales Report workflow** with a production-grade, database-backed system.

Public customer booking exists as a module but is secondary in this phase.

This is not a demo application.
This is an operational control system.

---

# 2. Problem Statement

The client currently operates using Excel sheets to manage:

- Daily bookings
- Room scheduling
- Therapist assignments
- Payment recording
- Discounts
- Revenue breakdown
- End-of-day reconciliation

Problems with Excel:

- Manual calculation errors
- No collision prevention for rooms
- No therapist scheduling safety
- No real-time dashboard
- No audit trail
- No branch-level operational visibility
- No financial immutability
- Difficult scaling across branches

The ERP must fully replace this workflow.

---

# 3. Product Vision

BookSpa will become:

> A branch-level operational ERP system with booking as one module,
> scalable to multi-branch and public booking in later phases.

Phase 1 Focus:
Replace Excel entirely for a single branch (Lazimpat).

# 6. Scope — Phase 1 ERP MVP

## 6.1 Included Modules

### A. Operational Dashboard (Primary Screen)

This replaces demo analytics.

Displays:
- Today’s booking count
- Paid bookings count
- Gross revenue (paid only)
- Total discounts
- Net revenue
- Revenue by payment mode
- Unpaid bookings
- Room utilization %
- Therapist workload summary
- Attendance summary

All metrics are real DB-driven.

---

### B. Booking Module

- Create booking (customer or staff)
- Auto-assign first available room
- Manual therapist assignment
- Booking lifecycle:
  - Pending
  - Confirmed
  - In-Progress
  - Completed
  - Cancelled
- Booking number auto-generated
- Overlap prevented via DB exclusion constraints

---

### C. Payment Recording

- One payment per booking
- Payment modes:
  - Cash
  - Nabil
  - GlobalIME
  - NICAsia
  - Fonepay
- Immutable payments
- No delete
- No update after insert
- Payment status: unpaid → paid

Revenue calculations use `payment_status = 'paid'`.

---

### D. Discount Workflow

- Staff can request discount
- Manager can approve
- Approval required for discount to persist
- Rejection resets discount_amount = 0
- Financial consistency enforced via DB constraints

---

### E. Daily Reconciliation Screen (Excel Replacement)

Must replicate Excel logic.

Displays:

- Total bookings
- Paid bookings
- Gross revenue
- Total discounts
- Net revenue
- Revenue by payment mode
- Revenue by therapist
- Room utilization (minutes-based)
- Unpaid bookings count

Export to CSV required.

---

### F. Room Scheduling View

Visual grid:

Rows: Rooms  
Columns: Time slots (09:00–21:00)  
Blocks: Booking segments  

Must reflect real DB state.

---

### G. Attendance

- Staff check-in
- Staff check-out
- Manager can view attendance by date

# 8. System Architecture

## Frontend

- React 18
- Vite
- Tailwind CSS
- Role-based routing
- Centralized API layer

## Backend

- Supabase (Postgres + Auth)
- Row Level Security
- GIST exclusion constraints
- Trigger-based financial enforcement
- Immutable payments

---

# 9. Core Database Rules (Non-Negotiable)

1. Room double-booking prevented via GIST exclusion.
2. Therapist double-booking prevented via GIST exclusion.
3. Payments immutable (no UPDATE, no DELETE).
4. One payment per booking.
5. Financial snapshot stored at booking time.
6. final_amount = base_amount - discount_amount (enforced via trigger).
7. booking_number generated by DB trigger.
8. Revenue metrics use payment_status = 'paid'.

---

# 10. Operational Constraints

- Single branch in Phase 1 (Lazimpat)
- 9 rooms
- 8 services
- 6 therapists
- 30+ bookings per day expected
- Must handle concurrent inserts safely
