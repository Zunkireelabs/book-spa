Production performance audit · Zenly

Why the booking app feels slow

The production database is small, healthy, and almost entirely in memory. Clients are not waiting on data volume — they are waiting on round trips, and on a row-security policy tree that costs more to plan than the query costs to run.

Date 12 Nov 2026 Target prod · pmbvogiphelmpjdalmtv Region aws-1-ap-northeast-2 Stats window 46 days

There is no single slow query and no overloaded server. Across the 46-day window the database spent well under 1% of one core on application work, and its cache hit rate is 100.00%. The system is slow because a typical user action is assembled from a long chain of individually expensive round trips.

Three multipliers stack: every request crosses from Nepal to Seoul instead of Mumbai; every payments read drags in a 442-node query plan built from nested row-security policies; and the service layer issues those requests one at a time rather than in parallel. Creating a booking fires 26 sequential database calls. Each of the three fixes is independent, and the first two are small.

Update, same day — findings 01, 03 and 04 are fixed. Findings 03 and 04 are code changes on the stage branch. Finding 01 is supabase/migration-317-flatten-payments-rls.sql, applied to staging and held for production: it is a row-security change, so it wants a review and a deliberate promotion rather than riding along with the next merge.

Measured results: first-paint JavaScript 985 KB → 288 KB gzipped; booking creation 26 → 19 round trips in 4 parallel batches; the dashboard insights panel 12 → 2; and the payments read 66.4 ms → 10.8 ms in identical conditions (about 1.8 ms once warm). Findings 02, 05, 06, 07 and 08 are untouched and still stand as written below.

Findings, ranked by user-visible impact

Ranked by how much latency each one removes from a real interaction, not by how alarming the raw number looks. Evidence is quoted verbatim from the production database and the production build.

01

Row-security policies on payments expand into a 442-node plan

Fixed

This is the single most expensive thing the application does, and it is pure overhead. payments carries three permissive SELECT policies. Postgres ORs them together, so all three are evaluated. Each one contains an EXISTS into bookings, which expands its own five permissive policies, each of which reaches branches, which expands four more — one of them a correlated subquery over customer_accounts. Three times five times four is sixty policy branches for one read.

The result is that planning the query costs roughly as much as running it, on a table holding 6,499 rows. The customer-facing policies are evaluated in full even when a staff member is reading, and vice versa.

EXPLAIN (ANALYZE) · role authenticated · manager JWT · 50 rows Plan nodes . . . . . . 442 (278 InitPlan / SubPlan entries) Planning Time . . . . 11.798 ms Execution Time . . . . 187.659 ms pg_stat_statements · payments.amount, payments.payment_mode WHERE booking_id = ANY($1) calls 49,635 mean 48.2 ms max 14,250.9 ms total 2,392.3 s → #1 application query by total time, by a factor of 3.3x
Done

Fixed on staging in supabase/migration-317-flatten-payments-rls.sql, held for production. The three OR’d SELECT policies are replaced by one calling a set-returning SECURITY DEFINER function, accessible_booking_ids(). A per-row predicate was tried first and measured slower than the original (planning collapsed, execution doubled) because such a function cannot be inlined and so runs once per row; phrasing it as booking_id IN (SELECT ...) makes the planner evaluate it once per statement instead. Same conditions, same user: 66.4 ms → 10.8 ms. Equivalence was verified by capturing the visible payment ids for all 22 staging users across four roles and five orgs before and after — identical for every user, and zero cross-org rows visible to anyone.

Fix

Collapse the OR'd permissive policies into one policy per table per command, with the role branches inside a single SECURITY DEFINER helper — e.g. user_can_read_booking(uuid) — so the chain flattens instead of multiplying. Gate the customer-facing policies on role so they are not evaluated for staff sessions. The existing scripts/check-rls-initplan.sh already passes (228 policies, no unwrapped helper calls), so this is about policy count and nesting, not the initplan pattern that was fixed previously.

02

The production database is in Seoul; the clients are in Nepal

Critical

Production runs on aws-1-ap-northeast-2 (Seoul). Staging runs on aws-1-ap-south-1 (Mumbai). Kathmandu to Mumbai is roughly 1,000 km; Kathmandu to Seoul is roughly 4,500 km. Every round trip in every finding below pays this distance, and finding 04 pays it twenty-six times for one booking.

Measured from the audit machine, the same SELECT 1 against each pooler:

Mumbai (staging) 0.32 s Seoul (production) 1.09 s

Three runs each: Mumbai 0.32 / 0.43 / 0.35 s, Seoul 1.02 / 1.09 / 1.25 s — roughly 3x, including TLS handshake. The ratio, not the absolute number, is the finding; the audit machine is not in Nepal, but the geography only gets worse from there.

Fix

Migrate the production project to ap-south-1, matching staging. This is a Supabase project migration with real downtime and a credential rotation, so it needs scheduling — but it is a configuration change, not an engineering one, and it reduces every single latency figure in this report by roughly two thirds.

03

The entire app ships as one 4.19 MB JavaScript file

Fixed

There is no code splitting anywhere. src/Routes.jsx has 31 static imports and zero lazy() calls, so Vite emits a single chunk containing every route. A customer opening the public booking page downloads and parses the manager dashboard, the payroll panel, the spreadsheet exporter and the charting library before anything renders.

npm run build · production build/assets/index-BJl8SxyN.js 4,190.85 kB │ gzip: 985.54 kB build/assets/index-CtzcoZIZ.css 99.17 kB │ gzip: 17.77 kB (!) Some chunks are larger than 2000 kB after minification. Confirmed inside the single chunk: recharts, xlsx, posthog-js, dompurify, lucide-react. FullCalendar and dnd-kit also route-only. src/Routes.jsx: 31 static imports, 0 lazy()
Done

Fixed. Every route is now React.lazy() behind one <Suspense>, with vendor chunks split in vite.config.mjs. The larger win was AppIcon.jsx: it did import * as LucideIcons and looked icons up by name, which defeats tree-shaking and shipped all 5,293 lucide exports for the 165 the app actually uses. It now reads from a generated allowlist (scripts/gen-icon-registry.mjs). First paint went 985 KB → 288 KB gzipped, and the login page now pulls the entry plus one route chunk instead of everything.

Fix

Wrap every route in React.lazy() behind a <Suspense> boundary, and add build.rollupOptions.output.manualChunks to split the vendor libraries. The biggest wins are route-only: FullCalendar and dnd-kit (calendar), recharts (reports), and xlsx (export). Target a first-load chunk under 300 KB gzipped. The chunkSizeWarningLimit: 2000 currently set in vite.config.mjs is suppressing this warning rather than answering it.

04

The service layer never parallelises — createBooking makes 26 sequential calls

Fixed

Across all of src/services/api.js (16,364 lines, 405 .select() calls), Promise.all appears in exactly one function. Everything else awaits one statement at a time. Most of these calls are independent lookups — service, branch, rooms, therapists, availability — that could be issued together.

Multiply the call count by the Seoul round trip from finding 02 and the policy cost from finding 01, and a single booking becomes a multi-second wait with the UI blocked.

Done

Partly fixed — the read-batching pass, not the RPC consolidation. createBooking is 26 → 19 awaits across 4 Promise.all batches: its three preflight lookups became one query via an embedded industries resource, and all four therapist pre-checks now go out together. getTodayInsights went 12 round trips → 2. Guard order and error precedence are unchanged, and the query operations were diffed mechanically before and after — identical apart from the intended embed. Still outstanding: the write-chain consolidation into RPCs, and recordPayment / assignTherapist / rescheduleBooking.

Fix

Two passes. First, batch the independent read phase of each function with Promise.all — mechanical, low risk, and it alone should cut createBooking roughly in half. Second, for the write-heavy flows (createBooking, submitGroupBooking, recordPayment) move the validate-and-insert sequence into a single Postgres function called over RPC, collapsing the chain to one round trip and making it atomic at the same time. submitGroupBooking and the group-creation loop at line 6125 also call createBooking once per person in a for loop, so the cost is per-guest today.

05

Repeated full scans of bookings, customers and staff_transfers

Moderate

The tables are small enough that Postgres chooses a sequential scan, and at this size that choice is usually correct. The concern is the volume: 124 million tuples read sequentially from a 8,980-row table means the pattern is being repeated constantly, and it will stop being correct as the data grows. staff_transfers alone was scanned 177,118 times — it is read on nearly every request.

pg_stat_user_tables · public schema · 46-day window table rows seq_scan seq_tup_read avg rows/scan bookings 8,980 16,503 124,081,392 7,518 staff_transfers 338 177,118 43,983,305 248 customers 2,768 16,146 40,185,253 2,488 services 452 1,644 739,317 449 Index idx_bookings_status: 0 scans — unused, droppable
Fix

Revisit after finding 01 — much of this volume is policy subqueries re-reading parent tables, so flattening the policies should remove it rather than requiring new indexes. Afterwards, re-measure and add a composite index only where a scan survives. Drop idx_bookings_status, which has never been used.

06

Multi-second stalls appear across unrelated statements

Moderate

Mean times are modest but maximums are not, and the spikes hit statements that have nothing in common — application reads, auth token writes, and the cron bookkeeping table alike. That pattern points at a host-level pause rather than any one query: most likely CPU credit exhaustion or a checkpoint on the shared-tenant instance.

Worst-case execution, 46-day window cron.job_run_details insert . . . . . . . max 41,138.8 ms pg_timezone_names . . . . . . . . . . . max 29,799.0 ms realtime WAL poll . . . . . . . . . . max 17,714.4 ms payments read (finding 01) . . . . . . max 14,250.9 ms bookings status update . . . . . . . . max 13,952.4 ms auth.refresh_tokens insert . . . . . . max 3,072.1 ms Instance: shared_buffers 256 MB · max_connections 60 max_parallel_workers_per_gather 1 → Micro tier
Fix

Check the CPU-credit balance chart in the Supabase dashboard for the production project. If credits are being exhausted, the instance needs a larger tier — the current Micro sizing has no burst headroom, and a client reporting "it froze for ten seconds" is almost certainly hitting this rather than any of the findings above. This one is observable but not provable from SQL alone, so treat it as a lead to confirm, not a conclusion.

07

nginx compresses at the weakest setting and has no Brotli

Minor

nginx.conf enables gzip but leaves gzip_comp_level at its default of 1. Caching and the SPA fallback are otherwise correctly configured — hashed assets get immutable for a year and index.html is never cached.

Fix

Set gzip_comp_level 6 and add application/wasm plus the font types to gzip_types. Pre-compressing the build output with Brotli and serving it via brotli_static typically saves another 15–20% over gzip on a bundle this size. Worth doing, but it is a discount on finding 03 — shrinking the bundle matters far more than compressing it harder.

08

audit_logs is 96% of the database and is never read

Minor

178 MB across 90,575 rows — about 2 KB per row — against a total application footprint of a few megabytes everywhere else. Its four indexes have logged 10 scans between them in 46 days. Write volume is low (143 rows in the last 24 hours), so this is a storage and backup cost rather than a latency one, but it distorts every size figure and slows restores.

relname rows total size idx_scan audit_logs 90,575 178 MB ~10 (4 indexes) bookings 8,980 6,744 kB 3,224,298 payments 6,499 1,488 kB 2,212,300
Fix

Decide the retention period, then add a scheduled prune — there is already a prune_cron_job_run_details job to copy the pattern from. Drop idx_audit_logs_table_name and idx_audit_logs_record_id unless a compliance query needs them. Check whether the row payload is storing full before/after JSON where a diff would do.

What is not wrong

Ruling things out matters as much as finding them — each of these is a plausible theory that the measurements disprove, and chasing any of them would waste the sprint.

✓

Data volume. The largest application table is 8,980 rows and 6.7 MB. Nothing here is slow because there is too much of it.

✓

Disk I/O. Buffer cache hit rate is 100.00% across 10,026,756 transactions. The working set is entirely in memory.

✓

Table bloat and autovacuum. Worst dead-tuple ratio is 8.0% on booking_therapists. Autovacuum and autoanalyze are both current. Zero deadlocks, 16 temp files in 46 days.

✓

Supabase Realtime. The WAL poller looks alarming at 3,263,077 calls and 20,825 s of total execution — but spread across the 46-day window that is 0.52% of one core. It is the largest single consumer and still nowhere near a bottleneck. 32 active subscriptions; the publication covers only bookings and notifications.

✓

Connection pool exhaustion. 21 idle authenticator connections against a 60-connection limit, with 2 active at sample time. There is ample headroom.

✓

The RLS initplan pattern. scripts/check-rls-initplan.sh passes clean against production: 228 policies inspected, no unwrapped helper calls. All four helpers are correctly STABLE and SECURITY DEFINER. That earlier fix held — finding 01 is a different problem in the same area.

✓

Static asset caching. Hashed assets are served public, immutable for one year and index.html is correctly never cached. Only the compression level needs attention.

Suggested order of work

Sequenced so that each step is measurable before the next begins, and so the cheap wins land before the one that needs a maintenance window. Steps 1 and 2 together should be the bulk of the perceived improvement.

First Flatten the RLS policies on payments, bookings and branches Finding 01. One migration. Re-run the same EXPLAIN (ANALYZE) afterwards and confirm the plan drops from 442 nodes to double digits. This is the highest ratio of latency removed to risk taken.
First Lazy-load the routes and split the vendor chunks Finding 03. Frontend-only, independent of the database work, so it can run in parallel. src/Routes.jsx plus vite.config.mjs.
Then Batch the independent reads with Promise.all Finding 04, first pass. Start with createBooking, recordPayment and getTodayInsights — the three users hit most often.
Then Confirm the CPU-credit theory in the dashboard Finding 06. Five minutes of looking at a chart, and it decides whether the instance tier needs to change before anything else is measured.
Schedule Move production to ap-south-1 Finding 02. Needs a maintenance window and a credential rotation, and it touches the promotion runbook in supabase/PROMOTION.md. Largest single improvement, longest lead time — start the planning now even though it lands last.
Cleanup Collapse write chains into RPCs; prune audit_logs; tune nginx Findings 04 (second pass), 07 and 08. Worth doing, but none of them is what the clients are feeling right now.

Method and caveats

Measurements were taken on 12 Nov 2026 directly against the production database (pmbvogiphelmpjdalmtv) over the pooler, using read-only queries only: pg_stat_statements, pg_stat_user_tables, pg_stat_user_indexes, pg_policies and pg_settings. The EXPLAIN (ANALYZE) runs were executed inside a transaction as SET LOCAL ROLE authenticated with a real manager's JWT claims, then rolled back. No data was modified.

Cumulative statistics have never been reset, so all totals cover the full 46 days since the postmaster started on 26 Sep 2026. Per-day and per-core figures in this report are derived from that window — the raw totals look far more dramatic than the rates they represent, which is why finding 04 outranks the Realtime poller despite the poller's larger absolute number.

Two limits worth stating plainly. The round-trip figures in finding 02 were measured from the audit machine, not from a client device in Nepal, so the ratio between regions is sound but the absolute numbers are not what an end user experiences. And finding 06 is inferred from the shape of the outliers rather than observed directly — it needs the dashboard's CPU-credit chart to be confirmed or dismissed.
