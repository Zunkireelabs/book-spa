### Decisions / deviations from the plan
1. **Write path is an RPC, not `.update()`.** The plan called for a plain
   `.update()` on `branches`. `branches` has RLS **enabled with SELECT-only
   policies** — no UPDATE policy exists for any role — so that update would
   have affected zero rows and reported success. Replaced with an admin-only,
   org-scoped `SECURITY DEFINER` function shaped like
   `update_org_booking_settings()`.
2. **Capacity gate keys on `therapistFilter?.therapistId`, not on
   `therapistFilter` being set.** The plan gated on `!therapistFilter`. But
   provider-profile's "Any professional" mode (`ConfirmStep.jsx:21`) submits
   `therapistId: null`, so the trigger *does* fire for it — the plan's gate
   would have left that path erroring at submit, exactly the bug being fixed.
3. **Flag predicate mirrors the trigger literally** —
   `b.therapist_id IS NULL AND b.created_by IS NULL`, not the plan's
   `t.id IS NULL`, which diverges if `therapist_id` ever points at a missing
   therapists row.
4. **`DROP` + `CREATE`, not `CREATE OR REPLACE`** — the RPC's `RETURNS TABLE`
   shape changes, which `OR REPLACE` cannot do. The body is migration-299's
   **verbatim**, pulled from the live stage function definition rather than from
   the repo: 299 and 300 are the ghosts noted in Addendum 2 and are not on this
   branch, so the repo's newest copy of this function (213) is two revisions
   stale and would have silently reverted the full-capacity block fix.
