### Fix #1 — Reschedule not atomic + silently dropped fields

- **`supabase/migration-243-reschedule-booking-rpc.sql`** — new
  `reschedule_booking(p_booking_id, p_date, p_start_time, p_therapist_id,
  p_room_id, p_reason)` RPC, `SECURITY DEFINER`, mirrors
  `record_group_payment()`'s (migration-178) all-or-nothing pattern: locks +
  rejects a terminal/locked original (`SELECT ... FOR UPDATE`), inserts a new
  `bookings` row copying every preservable column (discount fields,
  special_requests, companion/referral fields, booking_group_id — explicitly
  the fields `createBooking()` always drops on reschedule) except
  date/start_time/therapist_id/room_id/status/id, recomputes
  `therapist_name_snapshot`/`room_name_snapshot` for the *new*
  therapist/room (service snapshot fields carry over unchanged — service
  doesn't change on reschedule), then cancels the original with
  `cancellation_reason = p_reason`. Deliberately does **not** replicate
  `createBooking()`'s JS-side advisory checks (therapist transfer-window /
  attendance-absence / inactive-therapist validation) — those exist for
  friendlier error messages, not data integrity; the DB triggers
  (`check_room_capacity`, `check_branch_online_capacity`,
  `enforce_therapist_for_active_bookings`, `enforce_booking_immutability`)
  still fire on the INSERT/UPDATE regardless, since this runs through normal
  table DML. Verified by reading all 8 bookings-table triggers before
  writing the function (no column conflicts, no double-refund risk —
  `handle_booking_cancellation_refund` fires correctly off the cancel
  UPDATE).
- **Naming collision found during implementation**: `api.js` already
  exports a *different* `rescheduleBooking()` (line 3145 — in-place
  date/time UPDATE for the calendar's drag-and-drop flow, used 3x in
  `calendar/index.jsx`). The plan's suggested name would have silently
  shadowed it. New wrapper named **`rescheduleBookingAsNewBooking`**
  instead, with a comment at both definitions cross-referencing the other so
  this doesn't get re-confused later.
- Wired into both call sites: `booking-details-assignment-modal/index.jsx`'s
  `handleReschedule` (replaced `createBooking` + `updateBookingStatus` with
  one call), and `calendar/index.jsx`'s `handleEmptySlotClick` — split the
  `source.isReschedule` branch out from the plain-Rebook `createBooking`
  path entirely (early-return) rather than branching after a shared
  `createBooking` call, since Reschedule and Rebook now hit genuinely
  different functions.

## Focus: PR #371 fix-plan round 2 — gaps in round 1's own fixes

User (via a prior code review) found round 1's fixes above were themselves
incomplete: the reschedule RPC was unreachable, and the no-show fix missed
3 sites. Executed the supplied fix plan directly (file:line targets given).

- **`supabase/migration-245-reschedule-rpc-grant.sql`** — new migration.
  `migration-243`'s `reschedule_booking()` was created with no `GRANT
  EXECUTE`, so under Supabase's default-deny posture every
  `supabase.rpc('reschedule_booking', ...)` call from the frontend would
  fail with "permission denied for function" — the whole feature was
  unreachable despite passing build/tests. Added the same
  `REVOKE ALL ... FROM PUBLIC/anon` + `GRANT EXECUTE ... TO authenticated`
  pattern `migration-241`'s `mark_tips_distributed` uses, matching
  migration-243's actual 6-arg signature. New migration file rather than
  editing 243 directly, since 243 may already be applied to staging.
- **Root-cause bug found while wiring the 3 missed no-show sites**:
  `isNoShow()` (added last round) compared `booking.status` against
  Title-Case literals (`'No Show'`/`'Cancelled'`), but
  `transformBooking()` lowercases `status` on its way out — so the
  predicate silently returned `false` for every transformed booking object,
  including the one call site from round 1
  (`branch-staff-dashboard/index.jsx`'s quick filter) that looked fixed but
  wasn't actually matching anything post-transform. Fixed `isNoShow()` in
  `bookingTransformers.js` to lowercase `status` before comparing, so it
  now correctly handles both a raw DB row (Title-Case) and a
  `transformBooking()` result (lowercase) — this was a precondition for the
  3 fixes below to actually work, not just a style nit.
  - `BookingsViewPanel.jsx` — imported `isNoShow`; `filters.status === 'no
    show'` now filters with `isNoShow(b)` instead of literal `b.status ===
    filters.status`.
  - `CalendarBookingCard.jsx` — imported `isNoShow`; both the card and the
    `BookingHoverPreview` now compute `colorKey = isNoShow(booking) ? 'No
    Show' : booking.status` before indexing `STATUS_COLORS`, so a
    cancelled-as-no-show booking renders the grey No-Show color instead of
    the Cancelled color.
  - `BookingDetailsPanel.jsx` — imported `isNoShow`; the terminal-status
    banner label and the lifecycle-progress-bar text both swapped their
    `booking.status === 'no show'`/`'cancelled'` literal ternaries for
    `isNoShow(booking) ? 'No Show' : 'Cancelled'`.
- **`migration-244-services-requires-therapist.sql`** — corrected the
  header comment, which claimed to "replace" a `/sauna|jacuzzi|steam/i`
  regex check in `CalendarGrid.jsx`; no such regex exists on stage (that
  file reads the new `requires_therapist` column directly, added in the
  same migration) — this is net-new functionality backing the
  unassigned-column self-service badge, not a replacement. Skipped the
  plan's optional transformer-wiring cleanup (surfacing
  `requires_therapist` through `bookingTransformers.js` instead of
  `CalendarGrid.jsx` reading the raw row) — not currently broken, and
  would've needed threading a new field through the transformer's service
  shape, more than the "small diff" the plan gated it on.

### Feature 4 — service↔staff eligibility allow-list

`therapists.specialties` (text[]) was pure display, never enforced at
assignment. Built a generic allow-list mechanism (no current tenant needs
it yet, built ahead per explicit request) rather than hardcoding to the one
known case (Pregnancy Massage):

- **`supabase/migration-249-service-staff-eligibility.sql`** — new
  `service_therapists` join table (`service_id`, `therapist_id` composite
  PK, `ON DELETE CASCADE` both sides). Semantics: no rows for a service =
  fully open (today's behavior, zero change for any org that never
  configures this); ≥1 row = allow-list narrows to exactly those
  therapists. RLS copied from an existing `services`-joined pattern (read:
  any authenticated org member; write: manager/admin), joined through
  `services.org_id` since the table has no direct `org_id` column.
- `ServiceManagementPanel.jsx` — "Eligible staff" picker added to each
  service's edit form, wired to new `api.js` `fetchServiceTherapists` /
  `setServiceTherapists` (replace-all-rows-for-service semantics).
  **Deviation from plan**: built as a checkbox list, not `CustomSelect` —
  `CustomSelect` has no multi-select mode; the checkbox-list pattern is the
  one already established in this same panel for the Position picker, so
  this satisfies the actual design-system rule (no native `<select>`)
  without inventing a new control.
- **Deviation from plan — enforcement point**: the plan assumed
  `createBooking` has an auto-assign-by-gender branch around
  `api.js:5239-5343` that picks a therapist from a candidate pool; that
  block turned out to be room assignment only — the therapist id is always
  passed in explicitly by the caller (manual assignment or the UI), there
  is no server-side auto-pick to narrow. Enforced eligibility instead as a
  validation gate inside `createBooking` (rejects with
  `THERAPIST_NOT_ELIGIBLE` if the passed therapist isn't on the service's
  allow-list when one exists) — same protection, different mechanism since
  the assumed pool-narrowing code path doesn't exist. Shared
  `filterEligibleTherapists`-style helper used by both this gate and
  `TherapistAssignmentPanel.jsx`'s manual-reassignment list, per the plan's
  request to avoid duplicating the "empty = unrestricted" logic twice.
