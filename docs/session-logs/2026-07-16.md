### Design
Existing write-granting RLS policies check role equality against the literal `'admin'`
(or `IN ('manager','admin')`) — never a negated check — so a brand-new enum value is
automatically excluded from every write policy without touching any of them. Postgres
also OR's together multiple permissive SELECT policies on the same table, so read access
was granted via **additive, brand-new SELECT-only policies** rather than editing any
existing policy. Zero risk to existing admin/manager/staff write paths.

Traced (via subagent) every current SELECT policy across `rls.sql` +
`migration-012-org-rls-policies.sql` + `migration-044-payroll.sql` that uses an
`admin`-literal bypass, to make sure the new role's read coverage was exhaustive:
users, bookings, payments, daily_reports, attendance, therapist_attendance, audit_logs,
staff_compensation, payroll_runs, payroll_items. Tables with no role gate at all
(organizations, branches, services, rooms, therapists, customers, notifications,
staff_transfers) already grant org-wide SELECT to any authenticated org member — no
change needed there.
