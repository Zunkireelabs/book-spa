New ticket from the same peer session. Group booking was gated only by the
build-time `VITE_ENABLE_GROUP_BOOKING` env flag — no per-org admin control. Spec
was fully resolved by the peer: reuse `migration-248`'s existing generic
`update_org_booking_settings(p_key, p_value)` allow-list RPC rather than a new
table/RPC, just add `'enable_group_booking'` to the allow-list.

Built:
- `supabase/migration-309-org-enable-group-booking.sql` — `CREATE OR REPLACE`
  of the same function, signature unchanged, `enable_group_booking` added to
  the allow-list tuple. Applied to staging.
- `src/contexts/TenantContext.jsx` — `enableGroupBooking: org?.settings?.
  enable_group_booking !== false`. Deliberately `!== false` (default ON),
  opposite of `showStaffSelection`/`enableStaffRatings`'s `=== true` (default
  off) — group booking is already live for every tenant with the env flag on,
  so defaulting this new setting to off would silently kill it for all of them
  on ship.

  the spec, flagged to the peer**: the spec only named TenantContext (consumed
  by the customer-facing flow), but `BookingSettingsPanel.jsx` (the admin
  toggle UI) reads `org[toggle.orgField]` from `useOrg()`, a separate context
  that independently duplicates `showStaffSelection`/`enableStaffRatings` from
  the same `org.settings`. Without this addition the new toggle would have
  rendered with `undefined` (visually off) regardless of the actual stored
  value — necessary for the admin UI's initial toggle state to be correct, not
  a scope change.
- `src/pages/branch-manager-dashboard/components/MasterData/BookingSettingsPanel.jsx`
