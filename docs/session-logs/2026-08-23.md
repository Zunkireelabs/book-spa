## Follow-up: Migration 118 — security fix for cross-tenant revenue leak

Executed `docs/superpowers/plans/2026-08-23-platform-admin-security-fix.md` via `superpowers:executing-plans`, same branch/worktree. Post-implementation review found a HIGH-severity gap: four internal `SECURITY DEFINER` helpers behind `platform_get_revenue_rollup` had **no `is_platform_admin()` gate** and were directly callable by any authenticated tenant user with an arbitrary `p_org_id` — `platform_org_sales_base`, `platform_org_category_breakdown`, `platform_org_branch_breakdown`, `platform_commission_for_range`.

- **Confirmed the leak** on staging via `pg_proc.proacl`/`aclexplode`: all four functions had `authenticated` and `anon` EXECUTE grants (Supabase's default auto-grant on new functions, per migration-039's known gap — `REVOKE FROM PUBLIC` alone doesn't strip role-specific grants).
- **Added migration 118** (`supabase/migration-118-revoke-internal-commission-helpers.sql`): revokes `PUBLIC`/`anon`/`authenticated` EXECUTE on all four helpers; additionally re-`CREATE OR REPLACE`s `platform_commission_for_range` with a direct `is_platform_admin()` gate as defense-in-depth (the other three are `LANGUAGE sql` and rely on the revoke alone), then re-revokes it since `CREATE OR REPLACE` restores the default grant.
- Applied to staging directly via psql; re-ran the grant query — only `postgres`/`service_role` remain on all four functions (zero `authenticated`/`anon`/`PUBLIC` rows). `platform_get_revenue_rollup` itself is unaffected (calls the helpers internally as definer-owner, which keeps EXECUTE).
- `scripts/check-migrations.sh origin/stage` passes for 118. Committed (`3ac6d43`).
- **Deferred to the user** (needs a live staging browser session, not available headless): Step 5 (call each revoked helper directly as a real non-admin staff JWT via browser console, expect `42501` permission-denied) and Step 6 (confirm the platform dashboard still renders full breakdowns as the platform admin, proving the definer rollup still reaches the revoked helpers). ## Follow-up: fix/platform-auth-deadlock — auth-lock hang on /platform/* reload

New branch `fix/platform-auth-deadlock` off `origin/stage` (separate from the `feature/platform-admin-revenue-share` work above).

- **Bug**: `PlatformAuthContext.jsx`'s `onAuthStateChange` callback was `async` and `await`ed `checkAdmin()` (a `supabasePlatform.rpc('is_platform_admin')` call) directly inside the callback. supabase-js v2 holds an internal auth lock for the duration of the callback, so awaiting another auth-dependent call inside it deadlocks — any reload of `/platform/*` with a persisted session hung forever on "Loading…".
- **Fix**: made the `onAuthStateChange` callback synchronous — it now only calls `setUser(session.user)` on a session, or clears user/admin state and resolves `loading` when there's no session. Moved the `checkAdmin()` call into a separate `useEffect` keyed on `user?.id`, which sets `isPlatformAdmin` and resolves `loading` once the check settles.
- `npm run build` passes.
- **Verified against real staging** (no browser available headlessly, so used a Node script hitting the live staging Supabase project directly, since supabase-js v2's auth lock behaves identically outside a browser): sign in with the real platform-admin credential, persist the session to a shared storage object, then create a fresh client against that storage (simulating a page reload restoring a persisted session). With the old buggy pattern (`checkAdmin()` awaited inside the `onAuthStateChange` callback), the callback fires but the nested `rpc('is_platform_admin')` call hangs — confirmed a hard timeout (8s) reproducing the reported deadlock exactly. With the fixed pattern (sync callback, `checkAdmin()` called afterward from the separate `useEffect`), the same sequence resolves cleanly (`is_platform_admin` → `true`, no hang). Script and credential file were scratch-only, deleted after the run; `.env` (copied from the sibling repo root's `.env.staging` to point this worktree's dev server at staging for the session) also removed afterward — nothing staging-specific left on disk in this worktree.
