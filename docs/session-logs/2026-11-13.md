## 2. Production: Kamala Tamang / Susan Nagarkoti roster bug

**Reported:** client asked why Susan Nagarkoti showed `DAY OFF` on the calendar when her
attendance was marked Present and the roster had not been touched.

**Root cause — not the roster.** `src/pages/staff-detail/index.jsx:209` writes working hours
on *every* staff save, unconditionally. `workingHours` defaults to all-seven-days-off
(`:35`), and `fetchTherapistWorkingHours` (`api.js:7092`) also returns `isDayOff: true` for
any day with no row — so "never configured" and "never works" are indistinguishable. Editing
a staff member's phone or photo silently records that they never work, and the calendar
shades their column off permanently.

Evidence: Susan's 7 rows were written in one transaction at 2026-11-06 10:57 UTC. Only 7
therapists in all of production have roster rows; five have exactly one rest day (genuine),
two were all-seven-off (accidental) — Susan and Jeevan Shrestha. Susan had 6 days present and
123 bookings since Nov 4.

**Resolution:** the client set her real hours manually in production (10:00–18:00 Mon–Fri +
Sun, Sat off), verified in the live DB. Because the edit form loads existing hours before
saving them back (`:113`), she is now immune.

**STILL OPEN — the code bug is live.** Active staff with no working hours set, and therefore
one profile-save away from a blanked calendar:

| org | active | has hours | exposed |
|---|---|---|---|
| DemoSpa | 67 | 0 | 67 |
| Nuad Thai Spa | 42 | 12 | **30** |
| Khems Cleaning | 4 | 0 | **4** |

34 real-tenant staff. Fix needs two parts: don't write the sub-form the user never touched,
and stop returning `isDayOff: true` for days with no row. Captured as lesson 7.

## 3. Design mockups — staff access and tiered pricing

Two features the team is scoping, modelled on Timely (gettimely.com) and built as
**annotated design-spec boards** (scrollable canvas of captioned panels with small annotated
state-cards), matching a reference format the user supplied.

- Files created:
  - `docs/mockups/staff-access.html` — 6 panels: full screen in the Zenly app shell, row
    states, grant detail, link picker, empty/loading/error, rules & constraints.
  - `docs/mockups/price-tiers.html` — 6 panels: tier manager in the shell, tier-manager
    states, service price section, booking flow, empty/loading/error, rules & open questions.

### The finding that shapes staff access

**Zenly has two disjoint people-tables with no link between them.** Nuad Thai Spa:
`therapists` 63 rows (61 active) — calendar, bookings, payroll; `users` 16 rows — login
accounts, `role` enum, `pin`. **No FK in either direction, zero therapists have an email,
zero email overlap.** So the feature is first an identity-linking problem, then access
control: "Give access" creates a login for a staff member; "Link to staff" attaches an
existing login to an existing staff record.

Only **6 of the 16** accounts match a therapist by exact name. Two of those six match **two**
therapist rows each (Sushila Rai → Therapist/92 bookings and Manager/3; Trisha Acharya →
Therapist/58 and GRE/2), because the therapists table contains duplicate people — seven
duplicate names in total, the same class of problem as the Kamala Tamang merge.

### The decided model for tiered pricing

Tier pricing is a premium for **naming a specific staff member**. "Any available" charges the
service's base price; naming someone charges that person's tier price. The rejected
alternative ("price follows the person") is kept on the board as a labelled contrast.

Timely sets tier prices **per service, on each service's own edit page** — not in a central
services × tiers grid. That resolves the scale problem (196 active services × N tiers is an
unusable matrix) and the board was restructured to match.

Also confirmed: the proposed "price locks at booking time" rule is consistent with existing
behavior — `service-detail/index.jsx:369` already states that price changes only affect
future bookings because historical bookings carry snapshot fields.
