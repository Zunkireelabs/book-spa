## PROD INCIDENT: whole staff dashboard down with Postgres 25P02 (resolved)

User reported production (`zenly.zunkireelabs.com/nuad-thai-spa`, Lazimpat branch) failing — first the Calendar view ("Failed to Load Calendar"), then a second screenshot showing *every* dashboard widget rendering the same error:

```
current transaction is aborted, commands ignored until end of transaction block
```

Stage was unaffected throughout.

### Diagnosis

That message is Postgres `25P02` — it is never the *first* failure. It means an earlier statement in the same transaction errored and the transaction was never rolled back; every later statement on that connection is then rejected. The fact that *all* widgets failed identically (not just calendar) pointed at a poisoned pooled connection rather than any one query.

Confirmed on prod via `pg_stat_activity`: one backend, pid `2680364`, sat in state `idle in transaction (aborted)` on `BEGIN ISOLATION LEVEL READ COMMITTED READ ONLY` (PostgREST's standard read wrapper). Supavisor kept handing that same backend to unrelated requests.

A read-only subagent sweep first ruled out the obvious suspects: `getCalendarBookings` (`services/api.js:4506`) and its siblings `fetchAttendance` / `fetchBlocksForRange` issue only plain PostgREST selects — **no** `supabase.rpc()` anywhere on the calendar path — and no migration in 212–223 (including the untracked `migration-223`) defines a multi-statement function or `DO` block used by it. The app code was not at fault.

Root cause chain, established from prod config and `pg_stat_statements`:

1. `public.bookings` carries **5 PERMISSIVE SELECT policies**, which Postgres ORs together and evaluates for every candidate row.
2. Those policies called `get_user_role()` / `get_user_org_id()` / `get_user_branch_id()` / `get_user_branch_ids()` / `auth.uid()` **unwrapped**. An unwrapped STABLE function in a policy expression is re-executed *per row* instead of being hoisted to a once-per-query InitPlan. `get_user_role()` is itself `SELECT role FROM users WHERE id = auth.uid()` — a table lookup, per row, per policy.
3. Two read policies (`customer reads own bookings`, `customer reads own referral-linked bookings`) additionally run subqueries over `customer_accounts` / `customer_referrals`. Staff can never match them but they were still evaluated for every row. Note `customer reads own bookings` has `roles = NULL` (PUBLIC), so it applied to staff too.
4. Result on a mere 5,931-row table: `seq_tup_read` of 35.4M and `bookings` queries peaking at **6–7.5s** in `pg_stat_statements`.
5. The `authenticated` role's `statement_timeout` is **8s** (vs 120s for superuser). A query that tripped it aborted mid-transaction, and the connection returned to the pool without a `ROLLBACK`.
6. `idle_in_transaction_session_timeout` was **`0`** (disabled), so that poisoned backend would never self-clear — it needed a manual kill.

Stage escaped only by luck of never tripping the 8s ceiling on its own pool; it is the same code and the same policy shape.

### Fixes applied

1. **Immediate restore** — `SELECT pg_terminate_backend(2680364)` on prod. Dashboard recovered at once.
2. **Backstop** — `ALTER DATABASE postgres SET idle_in_transaction_session_timeout = '60s'` on prod (was `0`). A future poisoned transaction now self-terminates instead of hanging indefinitely. Stored setting confirmed in `pg_db_role_setting`; no role-level override exists for it, so it reaches the app's `authenticated`/`anon` roles. Applies to new backends — a session opened through the pooler may still report the old value until its backend recycles.
3. **Cause removal** — `supabase/migration-224-bookings-rls-initplan-perf.sql`: wraps every helper call in the 9 non-trivial `bookings` policies as a scalar subquery (`get_user_role()` → `(SELECT get_user_role())`, etc.) so Postgres hoists them into InitPlans. `anon_insert_bookings` is `WITH CHECK (true)` and was left alone.

### Notes on the migration

- `ALTER POLICY` leaves an omitted clause untouched, so UPDATE policies restate **both** `USING` and `WITH CHECK`; INSERT policies restate `WITH CHECK` only.
- Gotcha found by testing on stage first: `branch_id = ANY ((SELECT get_user_branch_ids()))` makes Postgres parse `ANY` in its *subquery* form and fail with `operator does not exist: uuid = uuid[]`. Fixed with an explicit cast — `ANY ((SELECT get_user_branch_ids())::uuid[])` — which forces the array form. The `--single-transaction` guard rolled stage back cleanly, so the bad attempt left no partial state.

## RLS audit: the 25P02 outage was systemic, not a `bookings` problem

Swept every policy in production for the unwrapped-helper pattern fixed in `migration-224`. Found it in **163 policies across 53 tables**.

The amplifier: `get_user_role()` is `SELECT role FROM users WHERE id = auth.uid()`, so every unwrapped call is a table lookup — executed per row, from policies on every table.

    users     27 rows   94,925,233 seq scans   857,969,052 tuples read
    branches   8 rows    2,448,653 seq scans    11,300,086 tuples read

A 27-row table was the hottest relation in the database. That is what pushed ordinary queries past the 8s `statement_timeout` and caused the morning's outage.

`supabase/migration-225-rls-initplan-sweep.sql` fixes all of them. Written as a **DO block rather than 163 literal statements on purpose**: staging and production have **diverged on 20 policies**, so a static script generated from one database would silently overwrite the other's definitions. Rewriting each policy from its own current expression preserves that divergence and makes the migration idempotent — and it adapted correctly, rewriting 149 policies on staging and 163 on production.

Measured on production data (rolled-back transaction, real manager principal):

| query | before | after |
|---|---|---|
| `count(*) customers` | 25.1 ms | 1.5 ms |
| `count(*) services` | 5.2 ms | 0.4 ms |
| `count(*) therapist_attendance` | 67.2 ms | 1.8 ms |
| `count(*) payments` | 281.4 ms | 44.8 ms |

Safety: **336 visibility comparisons** (56 tables × 6 principals — admin, admin_viewer, manager, staff, customer, anon) with **zero mismatches**, and zero unwrapped calls remaining on either database. Post-apply live check on prod confirms correct role scoping (admin 5943 bookings, admin_viewer 5925, staff 3274, manager 5, anon 0) and no aborted backends.

Applied to staging then production (ledger `225 | rls-initplan-sweep | 2026-09-25 15:24:48+00`). Recorded in the repo by PR #337.

## Outreach: closed the "visible but unusable" gap in prod

After #336 made Outreach visible in production, the feature was configured nowhere — zero rows in `outreach_provider_config`, `outreach_templates`, `outreach_rules`. Two consequences: nothing could be sent, and because the Rules tab disables its template dropdowns when no template exists (`No templates for this channel`), the feature could not even be configured through its own UI without hand-creating a template first.

`supabase/seed-prod-outreach-config.sql` seeds the minimum usable configuration for every org: one `email`/`resend` provider row, `win_back` + `review_request` templates, and matching rules.

Key decision: **every rule is seeded `enabled = false`, `send_mode = 'review'`.** Staging carries an `enabled`/`auto` rule (`demospa / review_request`); that shape was deliberately not reproduced, because applying it to production would have started emailing live customers on contact. Enabling outreach stays an explicit human action.

No credential is in the file — `outreach_provider_config` has no API key column by design (migration-106); the Resend key lives server-side in the Edge Function environment.

Applied to production (3 provider rows, 6 templates, 6 rules): **0 enabled rules, 0 messages generated.** Recorded in the repo by PR #338. Seed data, so CI never applies it — manual per `supabase/PROMOTION.md`.

### Two mistakes made and caught while building it

- **The safety guard was wrong.** The first draft raised an exception if *any* rule in the database was enabled. It fired on staging, which was the giveaway: once an operator legitimately enables outreach, a re-run of an idempotent script must not start erroring. Replaced with an informational `NOTICE`. The real guarantee is the literal `false` / `'review'` in the INSERTs plus `ON CONFLICT DO NOTHING`, not a global assertion.
- **The staging "dry run" was not a dry run.** The seed file self-contains `BEGIN … COMMIT`, so its `COMMIT` fired and the outer `ROLLBACK` was a no-op — staging went 2/3/3 to 4/8/8 rows. Verified benign afterwards: the five created rows were all disabled/review, pre-existing rows (including the operator-enabled auto rule) were untouched by `ON CONFLICT DO NOTHING`, and zero `outreach_messages` were generated. Lesson: a self-transacting script cannot be tested by wrapping it in an outer transaction.
