### Round 3 — white overscroll-flash fix

User reported a plain-white flash during trackpad rubber-band
overscroll/drag-scroll, reproduced on `/dashboard` generally (not just the
calendar route). Two causes found and fixed:

- **Genuine regression from round 1**: removing the old sidebar's row-flex
  wrapper (`flex flex-1 min-h-0`) left the calendar-grid div as a direct
  child of a column-flex container without `min-h-0`. Flex items default to
  `min-height: auto` (their content's intrinsic height), so on short
  viewports / when the denser round-2 toolbar wraps to 2 lines, the grid
  could refuse to shrink and push real content past the viewport, causing
  genuine page scroll. Fixed: `index.jsx`'s grid wrapper
  `flex-1 overflow-x-auto md:overflow-hidden` → `flex-1 min-h-0
  overflow-x-auto md:overflow-hidden`.
- **Pre-existing but exposed by the above**: `html` had no explicit
  `background-color` anywhere (`src/styles/tailwind.css` only set it on
  `body`), and separately, macOS trackpad rubber-band in Chromium-based
  browsers (Brave, confirmed via the user's screenshot) paints its own
  native glow/bounce during overscroll that ignores page background styling
  entirely — so even after adding an explicit `html { @apply bg-background;
  }` rule, the white flash persisted (confirmed via a follow-up screenshot
  on `/dashboard`, not calendar-specific). Fixed by adding
  `overscroll-behavior-y: none;` to both `html` and `body` in
  `tailwind.css`, disabling the bounce/glow effect outright rather than
  trying to recolor it.

### Round 2 — redesigned to create-new + cancel-old, matching Rebook's shape

User clarified the intended UX right after Round 1 landed: Reschedule should
behave like **Rebook** (create a brand-new booking, don't mutate the original)
but, unlike Rebook, **close the original booking afterward** instead of leaving
it untouched. This is a deliberate reversal of Round 1's design, and also of
this codebase's own prior direction — git history (PRs #255–258) shows
"Reschedule" used to silently create a duplicate instead of updating, was
fixed to call `rescheduleBooking()` (UPDATE) instead, and a later PR explicitly
titled "revert/rebook-not-reschedule" cemented Rebook=create-new /
Reschedule=update-in-place as two distinct, intentionally separate flows (see
the comment at `calendar/index.jsx`'s `handleRebookStart`, "not the
create-vs-update bug fixed in PR #255-257"). Confirmed via `AskUserQuestion`
that the user wants to re-diverge from that precedent on purpose (both for
the calendar modal and the non-calendar details page), not that Round 1 was a
misread of their ask — proceeded on that basis.

- **Removed** Round 1's inline slide-over panel and `rescheduleBooking()` call
  from `BookingActionModal.jsx` entirely (state, handler, JSX, the
  `onRescheduled` prop). Reschedule button now takes a new `onRescheduleStart`
  prop and, like the existing `onRebookStart`, just hands the booking back to
  the caller and expects the caller to close the modal.
- **`calendar/index.jsx`**: generalized the existing `rebookSource` "pick a
  slot" mechanism (mouse-tracking floating card, Escape-to-cancel, the
  `handleEmptySlotClick` create-booking branch) to carry an `isReschedule` +
  `originalBookingId` flag instead of adding a parallel copy of that whole
  mechanism. New `handleRescheduleStart` sets `rebookSource` with that flag
  and closes the modal, identical to `handleRebookStart` otherwise. In
  `handleEmptySlotClick`, after the new booking is created successfully, an
  `isReschedule` source additionally calls `updateBookingStatus(...,
  'Cancelled', reason: "Rescheduled to <date> <time>")` on the original —
  failure of that step only surfaces a toast (new booking already exists
  either way, nothing to roll back). Floating card label/aria-text now reads
  "Reschedule mode" / "Click to move" when `isReschedule` is set. Escape
  during reschedule-pick-mode just drops out of pick mode (no inline-form
  fallback exists anymore for this path, unlike Rebook's Escape handler).
- **`BookingDetailsPanel.jsx` + `index.jsx`** (booking-details-assignment-modal
  — no calendar grid to click a slot on here): kept the Round-1 date/time/

## Focus: Tips feature (v1 — record + display only)

User wants staff to be able to record a customer tip when collecting
payment (screenshot showed "Entered NPR 15,000" against a NPR 14,200 due —
the overage scenario). Confirmed up front with the user: tips are **not**
company revenue — a gratuity passed to staff, must stay visible for
cash-drawer reconciliation but excluded from every revenue number. Used
plan mode: an Explore agent mapped the existing payment/revenue/payroll
pipeline, a Plan agent drafted the implementation, then I read the actual
call chain myself before finalizing — which surfaced a real gap in the
agent's draft (see below) before any code was written. Four scope decisions
locked in via `AskUserQuestion`: no per-therapist attribution (log the
total only), a dedicated Tip field separate from the amount-due math (never
touches the OVERPAYMENT guard), v1 = record + display only (no payroll
wiring), no admin-correction RPC (immutable like `payments`, fixed by hand
in the DB if ever needed).

**Why a new table, not a `payments` column**: `payments.amount` feeds
`update_booking_payment_status()`'s trigger, `recordPayment()`'s OVERPAYMENT
check, `getDailySummary`/`getDailyOperationalReport`'s revenue totals, and
`generatePayroll()`'s commission math — and `recordPayment()` itself inserts
across up to 6 different tender-type buckets (plain Cash/Card, Membership
RPC, ReferralWallet RPC, ReferralVoucher RPC, VoucherWallet RPC ×2,
SessionPackage) in one submission, so there's no single "the payment row" a
tip could attach to. Went with a fully independent `booking_tips` table
instead, written as a second, best-effort call right after `recordPayment()`
succeeds — zero FK/trigger relationship to `payments`.
