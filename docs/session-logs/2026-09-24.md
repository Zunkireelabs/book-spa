### Bug 1 — RevenueCards crash on Today ↔ Yesterday switch (PR #307, `fix/revenue-cards-stale-shape-crash` → stage)
User reported the manager/admin dashboard (`/:orgSlug/dashboard`) throwing "Something went wrong" after selecting Yesterday then clicking back to Today.

- Root cause: `RevenueCards.jsx`'s `loadRevenue` is async. On the render right after `period` changes, `isDaily` flips synchronously from the new prop, but `data` still holds the *previous* fetch's shape (flat `{grossRevenue, netRevenue, ...}` from `getRevenueForPeriod` for Yesterday) until the new fetch resolves. The daily branch then read `data.today.netRevenue` off `undefined` → `TypeError`, caught by the route's `ErrorBoundary`.
- Fix: added a `shapeMatches` guard after the existing `if (!data) return null` — bails (renders nothing, same as loading) whenever the fetched shape doesn't match the current period mode, until the matching fetch lands.
- Verified via `npm run build`.

- Found `deleteBlock()`/`updateBlock()` already fully implemented in `services/api.js` (migration-212) but never called from any UI — the block overlay in `CalendarGrid.jsx` was `pointer-events-none` with no handlers.
- Added: a hover-visible delete button (asks this-occurrence-vs-whole-series via `window.confirm` when the block is part of a recurring series, since there was no existing lightweight non-modal confirm component to reuse — `ConfirmDialog.jsx` forces a mandatory reason field, wrong fit here), and a bottom-edge drag handle that live-previews height and snaps to the nearest 15 minutes on release, calling `updateBlock` with `scope: 'this'`.

Only one has a membership (`LZP-PCM-9861493942`, balance 65,380). `fetchRelatedUnpaidBookings` (`services/api.js:2026`) bundles siblings by `booking_group_id` with no `customer_id` check. Paying the combined total via the Membership tender succeeds for one booking's customer and raises the exception for the other's.
- User's call after seeing the real data: treat this as the same real customer re-entered under a new phone number, and build a manual merge tool (the existing "Potential Duplicates" auto-detector only matches by normalized phone, so it can never surface this pair).
