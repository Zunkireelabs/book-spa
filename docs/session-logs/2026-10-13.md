## Focus: group booking name/phone validation + fallback bug

Bug report: staff-side group booking quick-create (manager/staff calendar)
required name+phone for every person, when only person 1 ("booking contact")
should be required — persons 2+ should be optional and inherit person 1's
name+phone if left blank. The per-row UI placeholder already implied this
("optional" for persons 2+), masking that validation enforced the opposite.

Root cause: `groupValid` used `people.every(...)` over name+phone, requiring
all rows instead of just `people[0]`. `buildGroupPeople()` already had a
lead-fallback for name/email/gender but explicitly skipped phone (stale
comment: "no phone fallback here" — leftover from when validation forced
every row to have its own phone).

`compute_service_offer_pricing()`, migration-206).

    `effective_price_npr`.
  - `base_amount` / `final_amount` now use
    `Number(newService.effective_price_npr ?? newService.price_npr)` instead
    of raw `price_npr` — mirrors `createBooking()`'s logic, falls back to

No changes to `applyDiscount()` or the DB trigger (`compute_final_amount()` /
`chk_final_amount`) — unrelated and already correct.

## Focus: Messages dropdown + Merge/Block/Delete kebab menu on customer header

Timely reference showed a "Messages" dropdown (Send a message / View sent
messages) and a kebab (⋮) menu (Merge / Block / Delete) next to Edit. Before
building new UI, checked what already existed — most of this turned out to
already have real backend support, just no customer-detail-page entry
point:

- `sendCustomerMessage` (→ `outreach_send_manual` RPC) and
  `fetchOutreachMessages({ customerId })` already existed (used by the
  automated Outreach review queue) — reused directly for Send/View.
- `mergeCustomers(canonicalId, duplicateId)` already existed (used by the
  branch-manager Manual Merge panel) — reused directly, scoped to "merge
  someone else into the customer I'm already on" rather than a freeform
  two-sided picker.
- No "Block" or "Delete" existed. Added:
  - `setCustomerActive(customerId, isActive)` — toggles the same
    `is_active` flag every customer list already filters on
    (`fetchCustomersLightweight` etc.), so blocking hides the customer from
    search/booking while keeping full history. Reversible (dropdown item
    reads "Unblock" when already inactive).
  - `deleteCustomer(customerId)` — a plain row `DELETE`, deliberately not a
    soft-delete/RPC. `customers` has no `ON DELETE CASCADE` from bookings
    (or memberships/packages/vouchers), so Postgres rejects it with a
    foreign-key violation for any customer with real history; caught and
    turned into a message pointing at Block instead. Only actually
    succeeds for a customer with zero history — the only case this is safe
    without building a cascading soft-delete system.

Both Block and Delete route through the existing `ConfirmDialog` component
(always requires typing a reason before the action unlocks — that reason is
UX friction only in this case, not persisted anywhere, since no
`block_reason`-type column was requested or exists).

- `src/pages/customer-detail/components/CustomerMergeModal.jsx` — current
