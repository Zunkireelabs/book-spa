## 1. Calendar drag-reassign — stale therapist name in tooltip

### Diagnosis

User dragged a Pending booking (Zac Lawrence) from Manisha Thing's column to Asmita Pariyar's column. After drop + confirm:

- Card rendered under Asmita Pariyar's column header (visually correct)
- Tooltip/details panel still read `THERAPIST: MANISHA THING`

Two display fields, two sources:

| Display | Source |
|---|---|
| Card column placement | `bookings.therapist_id` (and `booking_therapists.therapist_id` for shared bookings) |
| Therapist name in card / tooltip | `booking_therapists` join if it has any rows, else `bookings.therapist_id` |

Trace:

- `CalendarGrid.jsx:379-381` — `therapistName = b.booking_therapists?.length > 0 ? ...join(', ') : (therapistMap[b.therapist_id] || null)`. As soon as the junction has *any* row, it wins for name resolution.
- `handleConfirmReassign` (`calendar/index.jsx:1604-1638`) for the non-shared cross-column path calls `rescheduleBooking({ newTherapistId: targetColId })`.
- `rescheduleBooking` (`api.js:1465`) updates `bookings.therapist_id` + `therapist_name_snapshot`, then step 9 only syncs `start_time`/`end_time` in `booking_therapists` — it never updates `booking_therapists.therapist_id`.

So a single-therapist booking that already had a junction row would: move column (driven by `bookings.therapist_id` = new), but display the old name (junction row still pointed at the old therapist). Matches the screenshot exactly.

`assignTherapist` (`api.js:684`) already does the right thing — it deletes and re-inserts junction rows when therapists change. The drag-confirm path doesn't go through `assignTherapist` for non-shared bookings, so the junction drift only surfaced on calendar drag, not on the explicit "Assign Therapist" modal.

### What was changed

| Layer | File | Change |
|---|---|---|
| API | `src/services/api.js` step 9 of `rescheduleBooking` | When `newTherapistId !== undefined`: delete junction rows for the booking and insert one fresh row with the new `therapist_id` + synced times. Otherwise (time-only reschedule): keep the existing "update times" behavior |

Mirrors `assignTherapist`'s junction-sync pattern. Shared bookings (`booking_therapists.length > 1`) never reach `rescheduleBooking` for the therapist change — `handleConfirmReassign`'s `isSharedReassign` branch (`calendar/index.jsx:1578-1603`) calls `assignTherapist` directly with the updated id list — so multi-therapist bookings are untouched by this fix.

`unassigned`/`null` reassignments correctly leave the junction empty (delete-only, no insert), which matches existing `bookings.therapist_id = null` behavior.

## Key Decisions / Lessons

1. **Two write paths for therapist assignment, only one was junction-aware.** `assignTherapist` (used by the explicit Assign modal) correctly syncs `booking_therapists`. `rescheduleBooking` (used by the calendar drag-confirm path for non-shared bookings) didn't. The "shared booking" branch in the calendar avoids this by calling `assignTherapist` directly — but the single-therapist branch went through the un-synced path. Worth auditing whether other mutation paths that touch `bookings.therapist_id` (e.g., quick-create, booking edit modal) also bypass the junction.
2. **Display name resolution falls back, placement doesn't.** `bookings.therapist_id` is canonical for column placement; `booking_therapists` wins for the *displayed name* once it has any rows. That asymmetry is what made the bug visible (column moved, label didn't). The trust-the-junction-when-present heuristic in `CalendarGrid` is fine — the fix is at the write side, keep the junction honest.
3. **No DB change required.** Pure frontend-only fix — `booking_therapists` table schema, RLS, and constraints are untouched. Promotion to prod will not need a DB hand-off.
