### Migration 229's reaper cadence changed before it ever shipped

`* * * * *` → `*/5 * * * *`, at the source rather than via a follow-up migration.

The every-minute cadence was **redundant**: migration 228 (same PR) sets
`idle_in_transaction_session_timeout = '60s'` on `authenticator`, and that timeout applies to
`idle in transaction (aborted)` just as much as to plain `idle in transaction` — an aborted
transaction is still an open one. Postgres already terminates a poisoned backend after 60s with no
reaper involved. The reaper only lowers *mean* detection time; the 60s timeout binds the worst case
either way. And the redundancy was not free — at 1-minute cadence this job alone adds 1,440
`cron.job_run_details` rows/day versus 288 at 5 minutes.

### Bug found and fixed while resolving #344

#344's curl fallback was `status="$(curl -s -o "$bodyfile" -w '%{http_code}' ... || echo '000')"`.
curl writes its `-w` output **even on non-zero exit**, so on a connection failure the substitution
captured both values and `status` became `"000000"`. Reproduced directly. That compares unequal to
`"000"`, so `elif [ "$status" = "000" ] || [ "$status" -ge 500 ]` never fired on a total outage — the
exact case the branch exists to catch.

**Severity, stated precisely:** it falls through to the `!= 200` branch, so `failures` increments and
the workflow still exits 1. A **misdiagnosis** bug, not a silent pass — the alert fires but reports
`unexpected status [HTTP 000000]` instead of the dedicated compute-exhaustion message that is the
point of #344's monitor change.

Fixed by dropping the fallback entirely (curl's `-w` always writes, and the step sets `set -uo
pipefail` without `-e`), and by collapsing #342's and #344's two separate curl invocations into one
that captures status, timing and body together via `-w '%{http_code} %{time_total}'` plus
`-o bodyfile`. Also documented why the 25P02 check must stay first in the ladder: PostgREST serves an
aborted transaction as HTTP 500, so testing status before body would miscount every 25P02 as generic
unavailability.

The merged probe loop is a **superset** of #342 and #344, carrying all five fail gates: `aborted`,
`unavailable`, `failures`, `over_5s`, `over_2s >= 3`.

### Two process defects found

**1. `scripts/check-migrations.sh` re-shallows the clone.** Line 11 runs
`git fetch origin "${BASE_REF#origin/}" --depth=1`, truncating local history to depth 1 on every
invocation. This silently breaks `git merge-base`, `git diff A...B` and `git log A..B` locally, and
produced every bogus `fatal: ... no merge base` hit this session — including one I initially dismissed
as harmless. CI is unaffected (fresh checkout each run). **Not yet fixed** — one-line change, deserves
its own PR.

**2. Merged onto a stale worktree base, twice.** `git fetch` in a worktree does not move `HEAD`. The
first time (#343) I caught it before committing; the second (#342) the push was rejected as
non-fast-forward, and I reset to `origin` and redid the merge. Both bad commits are gone and both
branches' commits were verified present afterwards. The rule: run `git log origin/<branch>..HEAD`
**before** merging, not after a failure. This hazard was already written into the plan's constraints,
which is what makes walking into it twice the notable part.
