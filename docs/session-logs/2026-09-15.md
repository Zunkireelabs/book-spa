## Focus: Fixing 6 review findings on PR #245 (couple-separate-rooms)

### Context
PR #245 (`feature/couple-separate-rooms` → `stage`) had already been reviewed adversarially in a

migration-171's capacity triggers). This session executed a pre-written implementation plan
(`docs/superpowers/plans/couple-booking-review-fixes.md`) to fix all 6, using the
subagent-driven-development process (fresh implementer subagent per task, task-scoped review

### Actions
6 commits added to `feature/couple-separate-rooms` (`9f3b2ed`..`ffd54cf`), each independently
task-reviewed as spec-compliant and approved before moving to the next:

- **New `src/services/roomOverrideHelpers.js`** (+ `roomOverrideHelpers.test.js`, 13 tests): two
  pure helpers extracted following this codebase's existing convention (siblings of
  `transferDedup.js`/`therapistBranchWindow.js`):
  - `resolveJunctionRoomId({ index, therapistId, overridesMap, existingRoomId })` — unconditionally
    nulls the room override at junction-row index 0 (the primary). Fixes: promoting a companion
    to primary (after removing the original primary) no longer silently carries over the old
    companion's stale room override, since `BookingActionModal.jsx` only ever builds override
    entries for non-primary therapists.
  - `countOverlappingRoomRows(rows, { branchId, date, startTime, endTime, excludeBookingId })` —
    room-overlap counting with a COALESCE-style row→parent-booking time fallback, matching
    migration-171's DB triggers.
- **`src/services/api.js`**:
  - `assignTherapist()`/`createBooking()` wired to `resolveJunctionRoomId` for junction-row
    `room_id` construction.
  - `checkOverrideRoomCapacity()` and both of `createBooking()`'s room-capacity pre-check paths
    (explicit-room, auto-assign) wired to `countOverlappingRoomRows`, so the JS pre-checks now
    count `booking_therapists.room_id` occupancy (companion overrides) alongside
    `bookings.room_id`, matching migration-171's stricter DB trigger — previously staff could be
    told a room was free and then rejected by the trigger on submit.
  - `assignTherapist()`/`createBooking()` now surface previously-swallowed `booking_therapists`
    insert failures as a non-fatal `warning`/`_therapistAssignmentWarning` instead of only
    `console.warn` — a booking/reassignment could otherwise end up with zero therapist rows while
    reporting success.
  - New guard: `createBooking()` rejects a couple-flagged service when `bookingGroupId` is set
    (server-side; the group-booking service pickers already filtered `is_couple` client-side only).
- **`src/pages/branch-manager-dashboard/components/calendar/index.jsx`**: `handleAssignTherapist`
  and `handleQuickCreateSubmit` now toast the new warning fields. Companion payload
  (`therapistRoomOverrides`/`companionName`/`companionPhone`) in both this file and
  `BookingActionModal.jsx` is now gated on the service being `is_couple` (not just "2+ therapists
  selected") — matches the gate already used for that UI section's visibility, so switching the
  service away from couple before saving no longer ships stale companion data.
- **Final whole-branch review** (opus, full diff since this plan's start) caught one Critical bug
  introduced by this session's own new code: `countOverlappingRoomRows()` compared
  `row.start_time`/`end_time` (`"HH:MM:SS"`, from Postgres) against the window `startTime`/`endTime`
  (`"HH:MM"`, from `addMinutesToTime()`/raw UI state) via plain string comparison — since
  `"11:00:00"` sorts greater than `"11:00"`, two bookings scheduled back-to-back in the same room
  were falsely flagged as overlapping (wrong `ROOM_FULL` on the explicit-room path, silently
  skipped room on auto-assign). Verified independently, then fixed in commit `ffd54cf`
  (`normalizeTime()` pads `HH:MM` to `HH:MM:SS` before comparing) with 2 new boundary-case tests;
  re-reviewed as addressed with no new breakage.
- Same final review surfaced 4 further Important + 4 Minor issues, deliberately **not** fixed this
  session — each is either pre-existing behavior this plan didn't touch, or explicitly outside the
  plan's stated 6-finding scope (YAGNI constraint): unbounded `booking_therapists` history fetched
  with only client-side date/branch filtering in the 3 companion-overlap queries; the new warning
  surfacing is only wired in 2 of ~9 `assignTherapist`/`createBooking` call sites (drag-reassign
  and several other dashboard pages still swallow it); `checkOverrideRoomCapacity`'s primary-room
  query excludes the edited booking on both sides while the DB trigger only excludes it on the
  companion side (pre-existing asymmetry); `assignTherapist`'s junction-table delete+reinsert is
  non-transactional (now visibly warned on failure, but not prevented). Recorded as follow-up
  candidates in the PR comment.
- `npm run build` and `npm test` (73/73) verified clean after every commit.
