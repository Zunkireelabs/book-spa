### 2a. Staff transfer bug — `users.branch_id` not synced

User reported that after using the in-app Transfer Staff action to move Roshan Rai from Lazimpat to Thamel, his login still showed Lazimpat.

**Root cause:** the `transfer_therapist()` RPC (migration-039 / migration-041) only flipped `therapists.branch_id`. The matching `public.users` row — which `BranchContext` reads on sign-in to set `profile.branch_id` — was never touched. UI never updated because the underlying DB row never moved.

**Immediate fix:** manual `UPDATE users SET branch_id = '<Thamel>' WHERE full_name = 'Roshan Rai'` on prod, resolved by name+slug (no UUIDs). User logged Roshan out + back in to refresh the cached profile.

**Permanent fix — migration 048 (`transfer-syncs-user-branch`):** adds a `_sync_user_branch_for_transfer()` helper and patches both `transfer_therapist()` and `apply_due_staff_transfers()` to also flip `users.branch_id` when there's a matching `role = 'staff'` user (case-insensitive name match, exactly one match required — zero or ambiguous skips silently with `RAISE NOTICE`). Manager/admin out of scope for now.

Bug surfaced in the migration draft: `max(uuid)` doesn't exist in Postgres. Smoke test on staging hit it immediately, and the same broken function was returning the error in the UI when user tried Roshan's transfer again. Fixed in-place on stage via `CREATE OR REPLACE` (two-step `count(*)` + `SELECT id` instead of bogus `max(uuid)`), then propagated to the repo file.

Applied to staging + production same session. Commit `ef4ecfb` → committed locally on `main` but stayed unpushed until the 2026-06-18 cleanup PR #55.

## Key Decisions / Lessons

1. **Frontend-only deploys ≠ feature complete.** Three times this stretch (049, 051, and the customer org-id family before that), the frontend went live before the DB policy did, leaving users with a usable affordance that returns `permission denied` on click. Each time the recovery was fine because the user pasted the SQL within minutes. But this is the same warning CLAUDE.md's `[!IMPORTANT]` block has been making for weeks: code promotion ≠ schema promotion. Worth keeping the explicit "DB hand-off REQUIRED" callout in every prod PR body.
2. **MCP token expires across sessions.** When MCP errors with "token expired", the fix is `claude /mcp` → supabase → Authenticate, in a **regular terminal** (not IDE-embedded). Worth noting because it cost ~3 minutes of confusion when it hit mid-task.
3. **Trust-the-API-layer pattern is now the established norm.** Three migrations in a row (049, 051, and the earlier customer-org-id family) take the shape "open RLS broadly + let api.js gate the columns/operations." It's the standard pattern for this app. Cleaner alternatives exist (per-column RLS via triggers, narrow per-operation grants) but add complexity without changing the practical attack surface — anyone with a manager/admin login can already open DevTools and call any Supabase RPC.
4. **`max(uuid)` doesn't exist in Postgres.** When picking a single representative row out of an aggregate, use two-step `count(*)` for the cardinality check, then `SELECT id ... LIMIT 1` separately. Or `ORDER BY ... LIMIT 1` if you actually want a specific row. The combined `count(*), max(<pk>)` shortcut fails for uuid PKs.
5. **Always state DB hand-off scope explicitly before opening a promotion PR.** Held the line on this from 2026-06-16's lesson. Membership migrations (045–047) and migration 050 were both correctly held back from every prod hand-off this session, even when nominally adjacent code shipped.
