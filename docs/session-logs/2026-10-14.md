### Security finding, fixed same session: cross-tenant RLS leak

Browser-testing the new panel (staging, logged in as the existing
nuad-thai-spa admin session already in this machine's Chrome) surfaced 3
"Unknown Branch" groups — these turned out to be **other orgs'** branches
(`demospa`, `sbal`, `khems-cleaning`): 33 bookings, real customer
name/phone/amount, visible to a nuad-thai-spa admin.

Root cause: `public.bookings` has two permissive SELECT policies that both
match role='admin' — `"Staff can read own org bookings"` correctly scopes
its admin clause with an org `EXISTS` check, but the sibling `"Staff can
read branch bookings"` has the identical `OR role='admin'` clause with
**no org check at all**. Permissive policies OR together, so the unscoped
one alone leaked every org's rows to any admin querying without a branch
filter — which includes the new Due Report, and the pre-existing
"Outstanding Report → Overall" admin view (`OVERALL_BRANCH_ID` already
no-ops the branch filter via `withBranch()`), so this was **already live
in production** before today, not something this feature introduced.

Same unscoped-admin-OR pattern also existed on the UPDATE and INSERT
policies for `bookings` (`"Staff can update/create branch bookings"`).

**Fix**: `supabase/migration-282-fix-admin-cross-org-bookings-rls.sql` —
dropped the redundant/unsafe `OR role='admin'` clause from all three
`"...branch bookings"` policies (SELECT/UPDATE/INSERT), since their
`"...own org bookings"` siblings already grant admins correct org-scoped
access on their own. User explicitly approved both writing and applying
the migration; applied to **staging** this session (confirmed via browser
re-test: cross-org rows gone, 164→131 bookings, no more "Unknown Branch").
**Prod still needs promotion** through the normal CI-gated `migrate` job
per CLAUDE.md — not yet applied to prod as of this entry. (One unrelated
pending migration, `migration-034-customers-merge-dryrun.sql`, auto-applied
alongside it as a side effect of `migrate-apply.sh` always applying
everything pending in order — a no-op, 0 rows affected.)

Browser QA used the existing seeded `admin@demospa.com` / PIN `1111` test
account (from `migration-demospa-seed.sql`) to confirm the real cross-org
leak scenario, then verified the actual nuad-thai-spa admin view via an
already-authenticated session already open in this machine's Chrome
(no credentials created or used for that part).

### Follow-up: FilterBar date-range row was wrapping to a 2nd line

User flagged (via screenshot) that the preset pills + date range + Apply
button wrap onto a second row on every report page — `FilterBar.jsx` is
shared by all of them, so one fix applies everywhere.

Root cause took two tries to find:
1. First pass added `lg:flex-nowrap lg:overflow-x-auto` to the row plus
   `flex-shrink-0` to its children — but the date-range wrapper div itself
   still used `flex-1` (`flex: 1 1 0%`), i.e. `flex-basis: 0%`. Adding
   `lg:flex-shrink-0` only stops *active* shrinking during overflow
   resolution — it doesn't change the 0% basis, so with constrained free
   space in the row the wrapper still rendered narrower than its own
   content, and that content (itself `flex-nowrap` internally) overflowed
   the narrow wrapper and visually painted over the next sibling (the
   "Apply" button showed as a cut-off "A" sitting under the "All Statuses"
   dropdown) instead of properly scrolling.
2. Real fix: changed the date-range wrapper to `lg:flex-none` (don't
   participate in flex grow/shrink at all at desktop width — just size to
   content) instead of fighting `flex-1`'s basis. Verified via
   `getBoundingClientRect()` in the browser console that the Apply button
   and the status dropdown were overlapping by ~45px before the fix, and
   fully separated after.
3. Also added `flex-shrink-0` to the `filters[]` dropdown wrapper, the
   "to" separator span, and the meta/count block, so the whole row now
   holds one line and scrolls horizontally (`lg:overflow-x-auto`) instead
   of wrapping or clipping when a page has more filters than fit (e.g.
   Discounts Report's extra Status dropdown).

Verified live across Outstanding Report, Due Report, and Discounts Report
(the one with the most filters) — all one line, scrollbar appears and
works when content overflows. Build/tests green.

## "Correct as admin" rebuilt: edit-all-fields + Discard/Save + double confirm

User wanted "Correct as admin" to let an admin edit every field of a
booking at once (not one field at a time), with the host dialog's footer
swapping to Discard/Save while correcting, and a confirmation step before
either discarding or saving.

Found `AdminCorrectionModal.jsx` already existed as the dedicated,
admin-only, audit-logged entry point past the lock/immutability banner —
but its UX was "pick one field from a dropdown, type one new value,"
reopened per field. The underlying RPC (`adminCorrectBooking` →
`admin_correct_booking`) already accepted a `changes` object with multiple
keys in one call — the one-field-at-a-time restriction was purely a UI
choice, not a backend limitation, so no API/migration change was needed.

Rewrote `AdminCorrectionModal.jsx`:
- All 7 `CORRECTABLE_FIELDS` (status, base amount, discount, date, start
  time, customer name, customer phone) render as editable inputs
  simultaneously, prefilled from the booking (`fieldsFromBooking()`,
  status converted DB-Title-Case via `toDbStatus()`). Each changed field
  gets an inline "changed" badge and amber border; footer shows "N fields
  changed."
- Footer buttons are now Discard / Save (previously Cancel / Apply) — same
  for the "Delete permanently" mode.
- `requestClose()` is shared by the header X and the Discard button: if
  nothing changed (no field edited, reason still empty) it closes straight
  away; if anything's dirty, it opens a lightweight local confirm overlay
  ("Discard changes? Nothing will be saved...") instead of a 3rd-party
  dialog, since the existing shared `ConfirmDialog` forces a mandatory
  reason textarea that doesn't fit a plain yes/no discard prompt.
- Save is gated the same way: validates reason length (still ≥10 chars,
  unchanged) and that ≥1 field actually changed, then opens its own
  confirm overlay ("Save these corrections? N field(s) will be updated...
  recorded in the audit log") before actually calling
  `adminCorrectBooking`/`adminDeleteBooking`.
- `changedFields` (the diff against the booking's current values) is what
  actually gets sent as `changes` — untouched fields are never included,
  so a correction only ever touches what the admin deliberately edited.
