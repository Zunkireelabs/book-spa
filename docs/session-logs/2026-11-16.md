## 1. Billing — VAT tax invoices (migrations 328–333)

New feature: issue an invoice for a paid booking and print it as A4 (browser
print-to-PDF, no PDF dependency) or to an 80mm thermal printer.

### Decisions taken with the user

| Question | Answer |
|---|---|
| Tax invoice or plain receipt? | **Full VAT tax invoice** |
| Thermal width | **80mm** |
| Tax treatment | **Prices include VAT** — extracted, never added |
| Who supplies the PAN | **The client**, through the admin UI |
| Billing on by default? | **No** — per-org toggle, default off |

### The arithmetic, which is where this could have gone wrong

Prices are VAT-inclusive, so VAT is **extracted from** the total, never added
to it. Adding 13% on top would have overcharged every invoice and desynced the
printed total from `payments.amount`.

```
vat     = round(final_amount * 13 / 113, 2)
taxable = final_amount - vat          -- NOT round(final_amount / 1.13)
```

Rounding both figures independently produces invoices whose lines don't sum to
their total. Done in integer paisa with BigInt and explicit half-up so the JS
preview matches Postgres `round(numeric, 2)` exactly — float rupee maths drifts
off it (20% inclusive on 200.13: SQL 33.36, float 33.35). At 13% inclusive this
client never hits a divergent case, but rate and mode are admin-configurable.
Verified across ten rates in both modes, ~3.8M comparisons, zero divergence.

### Design points worth remembering

- **An invoice is a snapshot, not a live render.** Printing from `bookings`
  would mean a reprint after any discount edit silently produces a different
  document under the same number. `issue_invoice()` freezes identity, lines,
  tax mode, rate, totals and footer onto an insert-only row.
- **`invoices` has no UPDATE, DELETE *or* INSERT policy** — rows can only be
  created through `issue_invoice`. Stronger than the commit message claimed.
- **Numbers and print ordinals are allocated database-side** (`ON CONFLICT ...
  DO UPDATE ... RETURNING`). Client-side `max()+1` hands two concurrent calls
  the same value — for a tax sequence that is a real problem, and for print
  ordinals it would print two ORIGINALs of one invoice.
- **Fiscal years come from a seeded table**, not a hand-rolled Bikram Sambat
  converter. There is no BS calendar library here, and a boundary someone can
  read and correct beats arithmetic nobody can audit.
- **The printed total must equal what was collected.** `issue_invoice` sums the
  booking's payments and refuses on mismatch, naming the gap.
- **`payments.booking_id` is NOT unique** — migration-042 dropped that for
  split payments. The peer caught this; the brief said otherwise. Totals are a
  SUM and `payment_mode` an aggregate of distinct tenders.
- **Nothing is defaulted.** Issuing fails closed until legal name, PAN and an
  explicit tax mode are set. This is multi-tenant; silently inheriting one
  client's tax treatment would misstate tax on another's invoices.

### Toggle (332)

Per-organization, not a `VITE_ENABLE_*` flag — those are per-environment and
would hide billing from every production tenant at once. Enforced inside
`issue_invoice()`, not just the UI, since the function is callable by any
authenticated session. Gate sits *after* the idempotent existing-invoice return,
so disabling blocks minting a new number but never orphans a past document.

## 2. Waitlist (migration 327)

Timely-style collapsible panel beside the calendar. Deliberately **not** a
booking with a special status: an entry has no slot, therapist, room or price,
so it would fail the state machine, conflict checks and payment rules.

Entries are never hard-deleted — no DELETE policy; removing sets status and
`removed_at`, and `booking_id` records what an entry became.

Booking someone in opens the normal Quick Create form prefilled, so tiered
pricing and conflict checks come for free. The entry flips to `booked` only
once the booking saves.

**Bug found in review and fixed at the chokepoint:** a restricted account sees
only masked name/phone, and those masked strings were being prefilled into the
booking form. `findOrCreateCustomer` matches on phone and overwrites
`full_name`, so every restricted-staff book-in would have collided on one junk
number and repeatedly renamed a real customer to asterisks. Fixed by adding
`knownCustomerId` to `createBooking`, which resolves the real record by id and
overwrites the caller's copies before any of it reaches a write.

**The rule this established:** masking is a display transform, and a display
value must never re-enter a write path.

## 3. Tiered pricing reaching the customer flow

User found this in the browser: the service list showed `NPR 1,200 - 8,600`
while the summary beside it priced the same service at a flat **8,200** — the
Unassigned rate, not even an endpoint of the range.

Cause: **two implementations of customer-facing price display**, and only one
knew about tiers. `ServicesSection.jsx` had a correct `servicePriceLabel`;
`bookingTransformers.js`'s `customerFacingServicePrice` knew only
`calendar_only` and fell through to `price_npr` for everything else — so
`tiered` showed the Unassigned rate, `free` showed a price, and `no_default`
showed a price it isn't supposed to have.

Now one function, returning a **string label** rather than a number, so a
caller cannot accidentally sum an unresolved tiered service. That type change
is what makes the bug class unrepresentable rather than merely fixed.

Six call sites migrated. The peer also found a gap not in the brief:
`BookingSuccess.jsx` never received therapist info at all, so it could not have
resolved a tiered price even with the helper fixed.

## 6. Staging data: the "Bold transformation" combo

Looked like a pricing error — combo advertised 7,000, components (GLOBAL COLOR
6,000 + Women's Hair Cut 800) sum to 6,800. It was not.

The user clarified that 7,000 is a "was" price and 6,800 the landing price. But
`offer_enabled` was **false**, so no discount was being displayed at all: the
customer saw a flat 7,000 and was charged 6,800. The discount was encoded in
the wrong field.

Applied to staging (one transaction, `scratchpad/combo-offer-fix.sql`):
- `offer_enabled = true, offer_type = 'fixed', offer_value = 6800` — so
  `price_npr` stays the list price and the offer supplies the sale price.
  Verified through `public_get_bookable_services('nuad-thai-spa')`: original
  7,000 / effective 6,800 / on offer.
- Deleted two `base_share_amount = 0.00` rows on `BK-20261016-0002`. They
  predated migration-326, were the only rows in `booking_combo_items`, and
  would have tripped F-4's check with a 7,000 gap had that booking been paid.

A VAT explanation was proposed and ruled out arithmetically: 6,800 × 1.13 =
7,684, and 200/6,800 is 2.94%, not 13%. Both sides are already VAT-inclusive,
so VAT cancels out of the comparison entirely.

**Open gap:** a combo is billed as the **sum of its components**, never from
its own price or offer. This works only because 6,800 equals 6,000 + 800. A
genuine bundle discount (say 6,500) would display one number and charge
another, and a component price change silently desyncs the offer. Making combo
pricing authoritative is separate work and should precede any combo promotion.

## 7. Follow-up audit fixes — migration 334

### F-9 — `invoices` bypassed both staff-access restrictions (322, 320)

The `invoices` read policy only ever checked `org_id` and `can_view_prices`.
Three separate gaps, all closed in one policy rewrite plus a new RESTRICTIVE
policy:

- **No RESTRICTIVE own-bookings policy.** An own-bookings-only account could
  read every invoice in the org — exactly the exposure 322 closed on
  `bookings` itself, never carried over. Added
  `"Own bookings only when restricted"` on `invoices`, resolving through
  `invoices.booking_id → bookings` and checking both `therapist_id` and the
  `booking_therapists` junction, the same shape as 322.
- **`can_view_customer_details` was never checked anywhere** — not on the
  read policy, not in `issue_invoice()`. The obvious fix (mask `buyer_name`
  the way booking lists redact) is wrong for a document the customer holds
  in their hand — `A***** T******` on a tax invoice is worse than refusing.
  Made it an access decision instead: `can_view_customer_details` gates both
  `issue_invoice()` (checked right after the existing `can_view_prices`
  check) and the read policy, and the print entry points
  (`BookingActionModal`, `CustomerSalesTab`) hide the button for those
  accounts.
- **No branch scoping for plain staff.** Added
  `branch_id = ANY(get_user_branch_ids())`, same function `bookings` already
  uses — manager/admin/admin_viewer keep org-wide reads so reports don't
  break.

### F-10 — `calendar_only` prices had a second door

Migration 333 nulled `calendar_only` prices in `public_get_bookable_services`
(the anon-facing RPC), but `services_with_offer_pricing` — granted to `anon`,
no `security_invoker` — still leaked them. Confirmed by reading the live view
definition: it has **no WHERE clause at all**; filtering only ever happened
via the base table's RLS, which this view bypasses entirely since it runs as
its owner (`postgres`, which has `BYPASSRLS`). Measured: 273 active services,
none currently `calendar_only`, so nothing leaks with today's data — the hole
opens the first time one is marked.

Fixed by nulling the same three price columns 333 nulled on the RPC, and
setting `security_invoker = true`. Checked all 4 `api.js` call sites first —
all authenticated, all already add their own `.eq('org_id', ...)` /
`.eq('is_active', true)` filters independent of RLS, so flipping the flag
changes nothing for any of them. (One mechanical snag: `CREATE OR REPLACE
VIEW` rejects a bare `NULL` in a `CASE` because it can't infer a matching
column type — needed explicit `::numeric(10,2)` / `::numeric` casts.)

### Verification

All three RLS scenarios simulated in rolled-back transactions as
`authenticated` with `request.jwt.claims.sub` set to a real staff user,
temporarily relinking `therapists.user_id`:

- own-bookings-only staff linked to the invoice's own booking's therapist →
  sees it (1 row).
- same staff relinked to a different therapist → sees nothing (0 rows).
- same staff back on the matching therapist but `can_view_customer_details =
  false` → still sees nothing — the gate holds even when the own-bookings
  check alone would have allowed it.

**Review caught a real bug in the first draft.** The policy applied
`can_view_customer_details IS NOT FALSE` unconditionally, justified by a
comment claiming the flag is "never toggled false on manager/admin — see
`StaffAccessPanel.jsx`'s `restrictable` guard." That guard is in `api.js`,
not a table constraint — migration-321's `users` UPDATE policy places no
restriction on the column, and `updateStaffAccess()` only normalises it when
the caller's payload touches the visibility fields at all. Promote a
restricted staff account to manager without touching those fields and the
role changes while `can_view_customer_details` stays `false`. That account
then gets a visible "Print invoice" button (the UI gate already uses the
privileged bypass) that always fails to read — visible control, failing
action. Fixed by giving the column the same privileged bypass
`resolveVisibility()` already uses (`role IN (manager, admin, admin_viewer)
OR can_view_customer_details IS NOT FALSE`), in both the read policy and the
`issue_invoice()` check, so the three layers (UI, policy, function) agree.
Verified with a 4th and 5th rolled-back-transaction case: a manager with the
flag forced `false` still reads the invoice and still calls `issue_invoice()`
without raising. The `updateStaffAccess` normalize-on-role-change gap itself
is still open — flagged as a separate tidy-up, not required for this fix.

View fix verified by flipping one real staging service to `calendar_only`
mid-transaction and querying as `anon`: that row's three price columns come
back null; the other 272 active services are unaffected. `npx eslint src` (0
errors), `npm test` (262/262, unchanged count), `npm run build` all pass.
Nothing in the transaction was committed.
