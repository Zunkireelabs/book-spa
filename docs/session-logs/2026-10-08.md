## Focus: Manual Merge can't find customers past 1000-row PostgREST cap

Prod bug report: duplicate membership customer ("Pratik Man Singh", two different
phone numbers, two real `customers` rows) not findable in the "Manual Merge" admin
tool's search box no matter how typed.

Root cause: `fetchCustomersLightweight` (`src/services/api.js`) ran a single
unpaginated `.from('customers')...order('full_name')` query with no `.range()`.
PostgREST caps unpaginated responses at 1000 rows server-side. With 1,506+
customers in at least one org, sorting alphabetically by `full_name` means rows
sorting late in the alphabet (e.g. "Pratik...") never made it into the in-memory
array that `CustomerAutocomplete` searches client-side — so no amount of correct
typing could surface them. (The automatic phone-collision duplicate detector is
unaffected/out of scope — these two rows have genuinely different phone numbers.)

### Files modified

- `src/services/api.js` — `fetchCustomersLightweight` (~line 8004): replaced the
  single unpaginated customers query with a page-until-short-page loop
  (`PAGE_SIZE = 1000`, `.range(offset, offset + PAGE_SIZE - 1)`), same pattern
  already used at `getServiceRevenueByBranch` (~line 1828). Kept the membership-
  status RPC fetch running concurrently via `Promise.all` alongside the new
  paging loop. No change to the enrichment/mapping logic after the fetch.

### Verification done this session

- `npm run build` — clean (same pre-existing >2000kB chunk-size warning only).
- Not tested against a live >1000-row org (no safe way to do so against prod
  data from this session) — pattern is identical to the already-proven
  `getServiceRevenueByBranch` implementation, so trusted by analogy.

### Not done / handoff

- Not yet merged to `stage` or deployed.
- Once deployed, needs live verification on production that "Pratik Man Singh"
  (both rows) now appear in Manual Merge search, then the admin performs the

- Flagged, not actioned: other unpaginated `.from(...)` queries in `api.js` may

## Focus: Edit/Add Staff modal — sticky header overlapping rounded corners

User reported (screenshot: `temp-ss/Screenshot 2026-10-08 at 19.09.19.png`) the modal's
header appeared to "stick" oddly against the modal frame. Prior two commits this session
(824c4563, 877d0e12) had capped the modal at `max-h-[90vh]` with `overflow-y-auto` on the
outer rounded card, and pinned the header inside that same scroll container with
`sticky top-0`. That combination is a known cross-browser corner-radius bug: a
`position: sticky` element inside an `overflow: auto` container with `border-radius` on
the container can render with square corners poking past the rounded edge once scrolled,
because the sticky element isn't reliably clipped by the ancestor's radius in all
browsers.

### Files modified

- `src/pages/branch-manager-dashboard/components/MasterData/TherapistManagementPanel.jsx`
  (~line 549–559, Edit/Add Staff modal): restructured from one scrolling card with a
  sticky-positioned header to a standard fixed-header/scrolling-body split —
  - Outer card: `overflow-y-auto` → `flex flex-col` (no longer the scroll container).
  - Header: `sticky top-0 z-10` → `shrink-0` (plain in-flow element, not pinned via
    position), added `rounded-t-spa-lg` so its own corners match the card's radius.
  - Body wrapper (`p.6 pt-4 space-y-4` div): added `overflow-y-auto` — now the sole
    scrolling container, so the header can never be visually clipped by it.
