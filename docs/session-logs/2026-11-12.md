### Method

Read-only queries only: `pg_stat_statements`, `pg_stat_user_tables`,
`pg_stat_user_indexes`, `pg_policies`, `pg_settings`, `pg_stat_activity`,
`cron.job`. The `EXPLAIN (ANALYZE)` runs were executed inside a transaction
as `SET LOCAL ROLE authenticated` with a real manager's `request.jwt.claims`,
then **rolled back**. Nothing was modified. Also ran
`scripts/check-rls-initplan.sh` against prod and `npm run build` locally.

Cumulative stats have **never been reset** — every total covers the full
**46 days** since postmaster start (2026-09-26 14:49 UTC). This matters: raw
totals look far more dramatic than the rates they represent, and reading them
without the window inverts the ranking (see "Realtime" below).

### Headline finding

The DB is **not** overloaded. Cache hit 100.00% across 10,026,756 txns;
largest app table is `bookings` at 8,980 rows / 6,744 kB. The problem is
**per-action latency**, not throughput — one user action is assembled from a
long chain of individually expensive round trips.

### Findings (ranked, as in the report)

1. **RLS plan explosion on `payments` — critical.** 3 permissive `SELECT`
   policies, OR'd; each does `EXISTS` into `bookings` (5 permissive policies),
   which reaches `branches` (4 policies, one a correlated subquery over
   `customer_accounts`). 3 × 5 × 4 = 60 policy branches for one read.
   Measured under a real manager JWT, 50 rows: **442 plan nodes**
   (278 InitPlan/SubPlan), Planning **11.798 ms**, Execution **187.659 ms**.
   In prod: 49,635 calls, mean **48.2 ms**, max **14,250.9 ms**, total
   **2,392.3 s** — #1 application query by total time, by 3.3x.
   *Not the initplan bug* — `check-rls-initplan.sh` passes clean (228 policies,
   no unwrapped helper calls; all four helpers correctly `STABLE` +
   `SECURITY DEFINER`). This is policy **count and nesting**.
   Fix: collapse the OR'd permissive policies into one policy per table per
   command, with role branches inside a `SECURITY DEFINER` helper
   (e.g. `user_can_read_booking(uuid)`); gate customer policies on role so
   they aren't evaluated for staff sessions.

2. **Prod DB is in Seoul; clients are in Nepal — critical.** Prod is
   `ap-northeast-2`; **staging is already `ap-south-1` (Mumbai)**. Same
   `SELECT 1` incl. TLS, 3 runs each: Mumbai 0.32 / 0.43 / 0.35 s vs Seoul
   1.02 / 1.09 / 1.25 s ≈ **3x**. Measured from the audit machine, *not* from
   Nepal — the ratio is sound, the absolutes are not. Fix is a project
   migration to `ap-south-1`: downtime + credential rotation, touches
   `supabase/PROMOTION.md`, so it needs scheduling.

3. **Single 4.19 MB JS bundle — critical.** `src/Routes.jsx` has 31 static
   imports and **zero** `lazy()`, so Vite emits one chunk:
   `index-BJl8SxyN.js` **4,190.85 kB / 985.54 kB gzip**. Confirmed inside it:
   recharts, xlsx, posthog-js, dompurify, lucide-react; FullCalendar and
   dnd-kit are also route-only. A customer on the public booking page
   downloads the manager dashboard, payroll panel and spreadsheet exporter
   first. `chunkSizeWarningLimit: 2000` in `vite.config.mjs` is currently
   suppressing this warning rather than answering it.

4. **Service layer never parallelises — critical.** `Promise.all` appears in
   exactly **one** function across all 16,364 lines of `src/services/api.js`
   (405 `.select()` calls). Sequential awaits / table ops:
   `createBooking` 26/18 (line 5356), `rescheduleBooking` 15/14 (3341),
   `assignTherapist` 15/12 (2225), `recordPayment` 14/6 (628),
   `getTodayInsights` 12/11 (3756), `updateBookingDetails` 11/8 (2576),
   `submitGroupBooking` 10 (6026), `getDailyOperationalReport` 8/7 (4095).
   `submitGroupBooking` and the loop at line 6125 call `createBooking` once
   **per guest**, so the cost is per-person. Multiply 26 round trips by
   findings 1 and 2 and a single booking is a multi-second blocked UI.

5. **Repeated full scans — moderate.** `bookings` 16,503 seq scans /
   124,081,392 tuples (avg 7,518 = full table each time); `staff_transfers`
   177,118 scans; `customers` 16,146 / 40,185,253. Correct plan choice at
   this size, but the *volume* says the pattern repeats constantly. Likely
   mostly policy subqueries re-reading parents — **re-measure after fixing 1
   before adding indexes**. `idx_bookings_status` has 0 scans; droppable.

6. **Multi-second stalls across unrelated statements — moderate, unconfirmed.**
   Max exec: `cron.job_run_details` insert **41,138.8 ms**,
   `pg_timezone_names` 29,799.0 ms, realtime WAL poll 17,714.4 ms, `payments`
   read 14,250.9 ms, `bookings` status update 13,952.4 ms. Spikes hit
   statements with nothing in common → host-level pause, most likely CPU
   credit exhaustion. Instance is **Micro**: `shared_buffers` 256 MB,
   `max_connections` 60, `max_parallel_workers_per_gather` 1. **Needs the
   dashboard CPU-credit chart to confirm — inferred from outlier shape, not
   provable from SQL.** Flagged to the user as a lead, not a conclusion.

7. **nginx compression — minor.** `nginx.conf` has `gzip on` but leaves
   `gzip_comp_level` at the default of **1**, and no Brotli. Caching is
   otherwise correct (hashed assets `public, immutable` 1y; `index.html`
   never cached).

8. **`audit_logs` is 96% of the DB and never read — minor.** 178 MB /
   90,575 rows (~2 KB/row); its 4 indexes logged ~10 scans in 46 days; only
   143 rows written in the last 24h. Storage/restore cost, not latency.

### Ruled out (measured, not assumed)

Data volume; disk I/O (100.00% cache hit); bloat/autovacuum (worst dead ratio
8.0% on `booking_therapists`, autovacuum current, 0 deadlocks, 16 temp files);
connection pool (21 idle authenticator conns of 60, 2 active); the RLS
initplan pattern; static asset caching.

**Supabase Realtime specifically:** the WAL poller is the largest single
consumer at 3,263,077 calls / 20,825 s total — but over the 46-day window
that is **0.52% of one core**. Not a bottleneck. 32 active subscriptions;
publication covers only `bookings` and `notifications`. Noting this because
the raw total is the most misleading number in `pg_stat_statements` here and
will look like the obvious culprit to the next person who reads it.

### Finding 01 — RLS flattening

- Files created: `supabase/migration-317-flatten-payments-rls.sql`
- **Applied to STAGING ONLY. Prod is HELD.**

Claimed migration number **317** after checking the live ledgers *and* every
remote branch (highest anywhere was 316) — per memory
`migration-number-collisions`.

Replaces the three OR'd `SELECT` policies on `payments` with one calling a
set-returning `SECURITY DEFINER` function `accessible_booking_ids()`. Both
INSERT policies untouched.

**The security subtlety, written down because it is easy to get wrong.** The old
"Staff can read branch payments" policy is `EXISTS (SELECT 1 FROM bookings b
WHERE b.id = payments.booking_id AND (b.branch_id = ANY(get_user_branch_ids())
OR get_user_role() = 'admin'))` — that `OR role = 'admin'` is **not org-scoped**.
It was safe only because the inner `bookings` subquery was itself filtered by
bookings' RLS, which *is* org-scoped. A `SECURITY DEFINER` function bypasses
that inner RLS — which is what makes it fast and what would turn this into a
cross-tenant leak. So `br.org_id = get_user_org_id()` is restated as a
**mandatory conjunct** in the function. Do not relax it.

**The performance trap.** The first implementation was a per-row
`user_can_read_booking(uuid)` predicate and it measured *slower than the
policies it replaced* — a `SECURITY DEFINER` function cannot be inlined by the
planner, so it ran once per candidate row plus its four nested helper calls.
Planning collapsed but execution roughly doubled. Rewrote it set-returning and
phrased the policy as `booking_id IN (SELECT accessible_booking_ids())` with no
correlation to the outer row, so the planner evaluates it **once per statement**
as a hashed SubPlan. Same staging DB, same user, same query
(`select amount, payment_mode from payments limit 50`):

| variant | planning | execution | total |
|---|---|---|---|
| three OR'd policies (original) | 41.785 ms | 24.648 ms | **66.4 ms** |
| per-row `SECURITY DEFINER` | 0.150 ms | 50.373 ms | 50.5 ms |
| set-returning (shipped) | 1.126 ms | 9.706 ms | **10.8 ms** |

Warm steady state afterwards: ~0.085 ms planning + ~1.69 ms execution over 5
consecutive runs. Prod plan was 442 nodes; staging after is 10.

**Equivalence proof.** Captured the exact set of visible payment ids (md5 of
the sorted id list + count) for **all 22 staging users** across all four roles
and five orgs, before and after. Reset staging to the original policies in
between and re-confirmed the baseline reproduced exactly, then applied the
rewritten migration and re-snapshotted. **Identical for all 22 users.** Separately
counted, per user under `role authenticated`, payment rows visible whose
`branches.org_id` differs from the user's org: **0**, summed across all users.
`anon` sees 0 payments. `scripts/check-rls-initplan.sh` passes (214 policies).

(One intermediate cross-tenant query in the transcript was malformed and ran as
superuser without RLS — it printed "22" and is meaningless. The valid check is
the per-user one under `role authenticated` described above.)

**Follow-up, not oversight:** `booking_combo_items` (3 policies), `booking_tips`
(2) and `payment_refunds` (1) nest into `bookings` the same way and can reuse
`accessible_booking_ids()`. Left out because `payments` is the only one measured
hot and a security change wants a small review surface.

**Scaling note recorded in the migration:** the function materialises every
accessible booking id once per statement. Fine at 8,980 bookings; if that grows
an order of magnitude, the right answer is probably a denormalised
`org_id`/`branch_id` column on `payments` so the policy needs no join.
