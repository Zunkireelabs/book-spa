### Conflict cost, and why it recurs

The promotion needed **15 conflicted files** resolved, including `api.js`.
Root cause: `merge-base(main, stage)` is still **2026-09-20**. Every promotion
is *squash*-merged, and a squash discards the commit that would link the two
branches, so shared ancestry never advances and drift re-accumulates. **This
cannot be fixed from inside a PR** — `required_linear_history` on `main`
rejects the merge commit that would repair it. Turning that setting off is the
fix; that call is the maintainer's.

## Process notes (mistakes worth not repeating)

- `git merge-base --is-ancestor` is the **wrong merged-check for this repo** —
  squash merges make merged branches read as unmerged. Verify by content.
- Promotions here are squashes, not true merges; that is the root cause of the
  recurring conflict, so do not describe them as merges in PR bodies (a "merge
  with a merge commit" line is impossible under `required_linear_history`).
- Promotion branches must **not** be named `chore/promote-…` — the Promotion
  Guard rejects it (cost a reopened PR, #351 → #352). Use
  `promote/stage-to-main-<date>`.
- The baselined ledger count is **27**, not 29.
- A `zsh` word-splitting bug in a verification loop produced bogus "IDENTICAL"
  results that had to be discarded and redone — quote expansions in
  verification loops.

## Later same day — root cause + fix for the 401, PR #354

The 401 triage above named the wrong suspect. Resolved with a fresh curl pass:
prod REST root (`/rest/v1/`) 401s **unconditionally** under the newer
`sb_publishable_` anon-key format regardless of key correctness — it's
PostgREST's discovery root behaving differently under the new key format, not
a stale/wrong/paused key. A real table (`organizations`) returns 200 with the
same key. Ruled out the token-rotation theory too, by querying prod
`auth.users`/`sessions`/`refresh_tokens` directly — login itself was healthy
throughout.

**Root cause:** `src/pages/login/index.jsx`'s health probe hit the bare
`/rest/v1/` root, which false-positives as "server down" under the current key
format — unrelated to actual DB health, and permanent (not transient) once the
key format migrated.

**Fix:** probe now hits `organizations?select=id&limit=1` instead. One-line
hunk.
