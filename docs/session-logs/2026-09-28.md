### Review pass — four gaps found and closed

Re-read the PR looking for logic gaps. Four surfaced; measurement closed all of
them, and one turned out to be a live hazard.

1. **PostgREST role-setting semantics — was an assumption, now sourced.**
   Whether `ALTER ROLE` on `authenticated`/`anon` actually binds per request
   was unverified. PostgREST's `references/transactions.rst` ("Impersonated
   Role Settings") states that PostgreSQL applies the connection role's
   settings (`authenticator`) and PostgREST additionally applies the
   impersonated role's as transaction-scoped overrides — with this exact pair
   of statements as its documented example. So all three lines are
   load-bearing and the impersonated value wins on the request path.

2. **`authenticator` at 30s was a live hazard.** `pg_stat_statements` on prod,
   worst statement per role:

   | role | worst | calls |
   |---|---|---|
   | `anon` | 86ms | 1,801 |
   | `authenticated` | 1,614ms | 177,566 |
   | `authenticator` | **29,799ms** | 38,641 |
   | `service_role` | 6,983ms | 33 |

   That 29,799ms is `SELECT name FROM pg_timezone_names` — PostgREST's
   schema-cache reload, which runs on the connection without impersonation —
   against a 30s ceiling. 99.3% of budget. Crossing it means the schema cache
   fails to build and PostgREST stops serving entirely, which is worse than
   the slow reload the ceiling was meant to bound, and it would happen exactly
   under the saturation the ceiling exists for. Raised `authenticator` to 60s.
   Because impersonated settings override it, the request path stays bounded
   at 30s / 3s — the loosening applies only to non-impersonated connection
   work.

3. **"Staging loses its canary" — measured away.** The request path's worst
   case is 1,614ms, so neither 8s nor 30s was ever reached in normal
   operation; no warning was actually firing. Real slow-query detection is the
   prod healthcheck workflow, gating at 2s and 5s — an order of magnitude
   below every ceiling here and unaffected by them.

4. **`anon` headroom quantified.** 86ms worst case against a 3s ceiling, 35x
   headroom, over 1,801 calls. The public booking path is not close to its
   limit.

**Rejected:** adding `log_min_duration_statement` per role as a staging canary.
`ALTER ROLE` accepts it, but `pg_settings` shows it is `context=superuser`, and
PostgREST applies impersonated-role settings via `set_config` inside every
request transaction — a role that cannot legally set it would error on every
request. Tested before shipping; an outage generator, not a canary.

Final values, re-verified by rollback dry-run on staging: `authenticator` 60s,
`authenticated` 30s, `anon` 3s, `service_role` unset (inherits 60s). The
role's other settings (`session_preload_libraries`, `lock_timeout`,
`idle_in_transaction_session_timeout`) survived intact.
